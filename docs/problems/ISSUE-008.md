## 1. 问题描述

供应商 print(data) 将字典写到 JSON-RPC 使用的 stdout，客户端解析失败。

## 2. 排查过程与原因判断

以下迁移原学习日志“问题 008：高德公交工具调试输出污染 MCP 协议（2026-10-08）”的完整问题记录。带日期的实现、调用、测试和Git状态是历史事实；后续变更以当前状态入口为准。原记录未列出的复现步骤或尝试不补造。

#### 原因与实现

本机 amap-mcp-server 的公交坐标查询在返回结果前执行 print(data)，把 Python 字典写入承载 JSON-RPC 消息的 stdout，引发客户端解析错误。项目增加 scripts/amap_stdio.py，通过 uvx --from amap-mcp-server python 加载；仅覆盖高德 server 模块的 print，丢弃原始响应，不修改 builtins、MCP传输实现或 uv 缓存。所有经 get_amap_mcp_tool 创建的客户端使用同一启动命令。该兼容适配针对当前供应商模块布局；以后升级供应商需复验。

#### TDD 场景与逐条记录

1. 协议完整：本地 FastMCP 测试工具打印字典，真实子进程/客户端交互中复现 Failed to parse JSONRPC message；首次未刷新输出时未稳定复现，改为 flush=True 确保污染抵达通道。测试失败后增加模块级输出适配，测试通过。
2. 原始数据不泄漏：新增断言发现移到 stderr 的方案仍记录原始响应，测试失败；改为丢弃该模块调试打印后通过。
3. 工具发现与失败保留：逐条新增真实协议回归，验证发现工具、成功→工具失败→再次成功，错误结果和后续正常结果均保留；当前实现直接通过，无需额外修改。
4. 启动异常可见：新增测试验证启动失败返回非零退出码、stdout为空、stderr保留错误；当前实现直接通过。

#### 验证边界

4项新测试及全量88项后端unittest通过；真实uvx使用已有缓存离线启动，假密钥下完成MCP握手与工具发现，共16项工具，不发起高德HTTP或模型请求。lifespan的IncompleteFieldDefinitionWarning仍存在，不在本次修复范围。本次未验证真实高德公交响应或整次规划耗时，未引入并行或连接复用。前端布局与项目全景HTML是此前任务的修改，保留未提交状态。

## 3. 尝试方案与方案结果

先用 flush=True稳定复现；转向stderr仍泄漏响应，最终仅丢弃供应商模块调试打印；协议回归通过。

## 4. 解决结果与验证边界

历史离线真实握手发现16工具；当次未做高德公交HTTP验证。

## 5. 经验总结

协议通道必须保持纯净；改用stderr也须检查内容是否适合记录。
