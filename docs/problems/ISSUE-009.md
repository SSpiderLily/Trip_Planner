## 1. 问题描述

相同 amap-mcp-server 版本在不同 Pydantic 环境中出现导入错误。

## 2. 排查过程与原因判断

以下迁移原学习日志“问题 009：uvx 环境更新 Pydantic 后无法启动（2026-10-08）”的完整问题记录。带日期的实现、调用、测试和Git状态是历史事实；后续变更以当前状态入口为准。原记录未列出的复现步骤或尝试不补造。

<details>
<summary>排查、实现与验证证据</summary>

对照两个本机缓存的包元数据：均为 amap-mcp-server 0.1.11（固定依赖 MCP 1.8.1），报错环境为 Pydantic 2.14.0，原可启动环境为2.13.5。在报错环境直接导入 FastMCP，复现 eval_type_backport ImportError。此错误发生在工具注册之前，与公交调试打印污染是不同问题。

TDD：先新增启动依赖约束测试，因启动命令未包含兼容版本而失败；再让 get_amap_mcp_tool 的 uvx 命令固定 amap-mcp-server==0.1.11，并用 --with pydantic==2.13.5 约束独立环境。该测试只验证启动配置契约，不替代真实兼容性验证。随后真实 uvx 离线握手和工具发现通过，共16项工具；全量89项后端测试通过。使用假密钥，未调用高德API或模型。未锁定全部传递依赖，升级时仍需启动验证；lifespan警告保留。

本次修改位于当前独立worktree；用户日志仍以bin/amap-mcp-server为入口，不能声称正在运行的其他目录已应用本次修复。未修改其他目录、清空uv缓存、提交或推送。

</details>

## 3. 尝试方案与方案结果

对比2.14.0与2.13.5环境，固定供应商0.1.11并约束Pydantic2.13.5；89项测试与离线握手通过。

## 4. 解决结果与验证边界

历史兼容启动通过；后续采用项目内vendor，旧启动命令不作现行推荐。

## 5. 经验总结

应用venv与uvx独立环境须分别检查依赖。
