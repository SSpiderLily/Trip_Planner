# ISSUE-020：派发合并出现事实ID冲突与餐馆复用范围错误

- 整理日期：2026-10-11
- 记录状态：离线修复已验证；当次在线受配额阻碍
- 范围：问题复盘；下方测试结果均为原记录中的历史证据，本次未重跑。
- 当前实现、验收及交付状态：[README](../../README.md)与[CHG-003](../changes/CHG-003-planning-performance-observability.md)；历史v3范围另见[CHG-002](../changes/CHG-002-trip-plan-enhancements.md)。

## 1. 问题描述

同POI补充字段仍使用固定事实ID，旧餐馆复用范围和候选目标也不一致。

## 2. 排查过程与原因判断

以下迁移原学习日志“主智能体派发中的事实版本与餐次范围（2026-10-11）”的完整问题记录。带日期的实现、调用、测试和Git状态是历史事实；后续变更以当前状态入口为准。原记录未列出的复现步骤或尝试不补造。

<summary>排查、实现与验证证据</summary>

- 问题：并行结果需要严格合并，但原组合事实固定使用POI派生ID，后续补充字段会触发同ID不同内容；旧餐馆只按日期复用又会在当前1公里餐次范围校验前失败。模型自行填写候选数量也会偏离既定目标。
- 修改：`planning_dispatch_service.py`调度依赖就绪任务，保留部分有效结果与明确结束原因；角色执行器按来源闭包生成组合事实版本，共享`candidate_identity.py`在绑定变化时生成新候选ID。Dining投影复用执行器的实际区域/餐次条件；全局旧事实和候选保留。主模型不重复接收全部搜索原文，候选数量由后端规则提供。
- 验证：根独立436项测试通过，包含并行隔离、局部失败、截止/取消、过期结果、严格身份冲突和复用范围。初次真实218.254秒，9次LLM/4次MCP后因候选目标错误停止；保留其事实继续验证时529.313秒，20次LLM/10次MCP后遇事实ID冲突，已知usage为417231/67127/484358，另1次LLM缺usage，因此不是完整用量。Dining局部异常进一步定位为工具前CANDIDATE_REF_INVALID；对应回归均已修复。
- 外部阻碍：修复后首次模型调用两次均快速返回403；安全异常链确认PermissionDeniedError并含quota信息。模型响应未知，0次新MCP成功调用；没有用离线通过冒充修复后真实成功。证据保留在临时目录`/private/tmp/trip-remaining-review/f05b-*`，未提交模型原文或密钥，未写正式数据库。

## 3. 尝试方案与方案结果

组合事实按来源生成版本，候选绑定变化生成新ID，复用实际餐次区域条件；436项回归通过。

## 4. 解决结果与验证边界

历史在线先遇候选目标错误，再遇事实冲突；修复后403阻碍真实成功复验。

## 5. 经验总结

身份相同不表示事实版本相同；复用应遵守当前条件。
