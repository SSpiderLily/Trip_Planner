## 2. 已确认的产品规则

### REQ-001 输入与全局条件

输入目的地，在选日期时同时选择到达、离开时间，补充偏好后生成。取消出发城市、城际班次票价查询、往返方案比较及自动回填；数据API不采用付费服务。

到达/离开地点选填，分别判断：未填的一端不计算、不显示接驳，也不提示接驳未知；填写则计算接驳，已填但查询失败应提示。到离完整日期时间始终约束首尾安排，同日旅行同时应用两端。系统内部默认预留缓冲，不提供用户输入或调整控件，不细化机场、车站规则。

首页出行偏好保持现有设计：默认公共交通结合步行，通过“其他要求”表达偏好，由模型理解，不新增四选一控件。初次规划据此选择景点、分布与交通；先尽量安排紧凑路线，仍不合适时允许采用其他方式并简述原因。

目的地、到离日期时间、预算、住宿、首页偏好等全局条件不在结果页编辑；改变这些条件应重新生成。普通活动窗口默认09:00—19:00，首尾日叠加到离约束；不新增细碎规划输入。

### REQ-002 费用与参考预算

保留可选的人民币人均全程参考预算，包含独住住宿、餐饮、景点门票，不含任何交通费用。初次推荐尽量贴近预算，生成或编辑后超预算只提示，不删改已选景点。

费用只使用查询到的数据，平台参考价格可以直接作为参考展示，不追求成交价保证，不增加复杂的用户侧价格分类。没有数据统一显示“未查询到真实数据”，禁止模型补价；未知不为零。数据不全仅展示已知费用小计，不声称全程符合预算。

保留住宿区域推荐；已填酒店则使用该酒店。住宿按独住口径，仅有可解释为房/晚的价格才可乘晚数，不能把POI人均消费生硬当成房价；匹配入住条件的数据可用时优先使用。无法确定单位或适用条件则保持缺失，无须为此接入票务/酒店交易系统。晚数默认离开日期减到达日期，同日为0；结果页不新增住宿条件编辑。

餐饮以顺路用餐区域为主，不强制指定店铺；查询到具体餐厅可展示其信息，不虚构推荐菜与消费。当天重排可调整推荐区域，用户明确指定的餐厅保留。

### REQ-003 景点编辑与地图

结果页允许当天景点新增、确认后删除、上移/下移，以及单段交通切换。游玩时长只展示系统参考值，可由模型建议，不提供用户修改入口；切换交通不能静默缩短停留。

地图搜索限定目的地城市，拖动地图不改变搜索城市。点击搜索结果仅定位并展示详情，点击“加入当天”才加入当前所选日期。新景点自动选择插入位置，保持原有景点相对顺序；比较新增交通耗时，并在有依据时考虑开放时间。无位置能在预估时间内容纳时仍保留新增景点并提示“可能超时”，不跨天移动或自动删除。

同一天按POI身份去重，已存在的地点显示“已加入当天”；其他日期出现过时提示所在日期但允许加入。删除前必须确认，取消不触发变更；必去景点也允许用户删除，确认后撤销该地点在本次行程中的必去要求，不自动补回或提示其未安排，其他必去要求不受影响；删除最后一个景点保留空白日，不自动补回，清理失效路线并更新餐饮/费用。

切换日期时左侧列表和地图同步展示当天，保留搜索关键词，关闭上一个日期的地点详情。列表立即响应编辑，短暂停顿后统一重算；失败保留最新编辑列表，受影响的旧路线与时间不得作为当前有效结果展示，提示可重试。

### REQ-004 路段交通参考

所有纳入行程的路段均提供步行、骑行、公共交通的可用耗时预览，包括景点、餐饮、住宿及已填的到离地点。自驾行程增加驾车方案。不做导航，不追踪车辆位置，不推演停车取车。

| 场景 | 默认采用方式 |
| --- | --- |
| 初次生成 | 优先符合首页偏好；同时标记耗时最短的方式；必要时可合理采用其他方式 |
| 用户手动切换某段 | 保留该段选择，更新当天后续预估时间；可能超时也不自动换回 |
| 新增、删除、排序产生新路段 | 采用有效数据中预计耗时最短的方式，自驾无特殊例外 |
| 编辑后起终点未变的路段 | 保留原选方式，包括手动选择；重新查询耗时不等于重新选择方式 |
| 最短耗时相同 | 优先符合首页偏好，其次步行；仍相同用固定顺序保证稳定 |
| 原选方式查询失败 | 保留选择，显示暂无耗时数据，列出其他可用方式，不自动替换或按零算 |

“当前采用”和“最快”分开显示；无法查询的方式不参与最快比较。时间均为参考；已知安排过满用“按当前预估，可能超时约X分钟”，给出可选节时方式，不声称实际必然迟到。含未知路段时说明暂不能完整判断；若已知部分已过满可同时说明已知预估部分的超出量。

### REQ-005 地点详情、开放与天气

简介、建议游玩时长可由模型生成并标明参考；地址、开放、预约、菜单、价格等事实应有查询依据。查不到开放时间就显示未查询到，不推断营业状态。

初次规划尽量参考已知开放时段和逐日预报；生成后开放冲突仅提示，天气只提供出行建议，不自动替换景点或改顺序。季节建议与逐日预报区分，预报不覆盖与查询失败分别处理，不能借用其他日期天气。

### REQ-006 独立导出

导出是可选功能，只把当前展示的行程转换成图片，不校验规划、不拦截冲突、不触发重排、不修改内容。费用缺失、可能超时、开放冲突或空白日均照常导出并保留当前提示。编辑中或重算失败时也不增加规划前置门槛，按当前可见内容及更新状态输出，不拿旧快照替换当前列表。

普通行程一张长图，过长按日期拆多张，导出前提示数量；单日过长可按活动块拆分并保留日期标记。不截断关键内容、不缩成无法阅读的小字，不以地图截图替代行程图片。

### 范围边界

不新增服务端编辑版本持久化，原始生成结果保留；不承诺跨设备或刷新后的编辑恢复。可沿用浏览器现有临时缓存，但不得把原始结果误称为修改后的最新版本。无额外用户账号、微服务、Agent角色、实时导航、预订支付、跨城市规划、手动时长编辑、模型价格估算或全局条件的结果页编辑。

页面区分两类行程提示：“可能需要调整”（可能超时、开放冲突、参考费用超预算）与“信息未查到”（价格、耗时等缺失）。两类均不阻止查看、局部编辑或导出；缺失不直接判为冲突。

## 3. 技术设计

领域术语统一使用“行程”，不引入“原始行程／当前行程”的分类。行程可处于路线待更新或查询失败状态；下文“原始生成结果”仅描述存储行为，不作为产品概念。导出使用用户当前展示的行程。

### 3.1 模块职责与现有差异

沿用Vue、FastAPI、HelloAgents、SQLite和异步规划任务。现有 `route_planner.py` 固定每天600分钟、费用含市内交通不含住宿；新版 `RouteResult.vue` 从sessionStorage读取结果、一次展示一天。旧 `Result.vue` 的截图代码不能直接覆盖新版编辑和多日导出需求。

| 模块 | 职责 |
| --- | --- |
| `models/itinerary.py`、`schemas.py` | v3请求/响应与明确嵌套类型，拒绝非法日期、数量、方式；历史结果不重解释 |
| `route_planner.py` | 初次模型理解、候选、分布与用餐安排；调用公共计算服务生成结果 |
| `services/route_options_service.py`（拟） | 地图适配、候选归一化、有限缓存、路线选择规则 |
| `services/schedule_service.py`（拟） | 顺序排时、插入位置评估、边界及可能超时判断 |
| `services/cost_service.py`（拟） | 真实查询价格的统一单位与费用汇总 |
| `services/day_edit_service.py`（拟） | 增删、排序、切换操作；核实POI，保留不变量，重算目标天 |
| `Home.vue` | 日期时间、预算、可选到离地点；保留现有偏好交互 |
| `RouteResult.vue`与拆分组件 | 地图搜索详情、当天列表、交通候选、编辑状态；独立导出组件 |

开放备注由模型理解，程序不以关键词推断意图。程序控制POI事实、金额、时长计算和编辑不变量。新增服务按职责适量拆分，不为每个字段建抽象层。

### 3.2 数据契约与兼容

新增结果 `schema_version: 3`（不同于本文件需求版本v4）。旧v1/v2结果保持原口径只读展示；新编辑只面向v3。创建接口新请求必须有arrival_at/departure_at，缺失返回422，不给旧日期请求静默补实际时刻；前后端同批更新。保留旧日期字段时仅作兼容校验，不能形成两个互相矛盾的数据源。

| 数据 | 关键字段 |
| --- | --- |
| 创建请求 | city、arrival_at、departure_at、可选arrival_place_id/departure_place_id、budget_per_person、已有lodging/preferences/free_text_input |
| 规划条件 | Asia/Shanghai时区、派生日期天数、模型理解后的交通偏好、系统缓冲、原备注 |
| 活动 | 稳定activity_id、类型、POI、duration_minutes、参考start/end、详情、查询消费、用户指定标记 |
| 路段 | 有方向的起终点身份、options、selected_mode、selection_source、fastest_mode、数据状态 |
| 交通候选 | mode、duration_minutes/null、distance/null、available/no_route/failed状态、source、queried_at |
| 费用项 | category、amount或查询返回的range、currency、unit、quantity、source、missing状态；不设模型估价来源 |
| 日汇总 | known_minutes、unknown_count、possible_overrun_minutes、reference_status、cost_summary、issues |
| 编辑 | task_id、date、edit_token、request_id、client_revision、有序operations（最多20项） |

坐标由服务端核实，不能信任客户端提交的名称或坐标。金额使用Decimal或整数分；免费必须有明确依据。时间用带时区完整值，本地自然日计天数，最多30天。未知耗时不转0，也不生成伪精确的后续时刻。

### 3.3 时间轴与插入算法

初次规划以09:00—19:00为普通窗口，叠加首尾边界；内部缓冲工程初值为到达后30分钟、离开前30分钟，通过后端配置管理、不提供前端输入。此数值是实现默认值而非用户指定或交通保障，不与原有每日固定30分钟机动重复累计。模型安排的自由活动独立计时。

填写到达点时：到达时刻＋内部缓冲＋接驳后进入首个活动；未填则从首个活动起算，不创建零耗时接驳。末日有离开点则检查最后活动＋接驳＋离开前缓冲，无地点则只检查活动结束与预留时间。首尾同日合并约束；中间日采用住宿参考点。迟到/早离可形成无景点日期，不强行填满。

编辑固定现有景点及参考停留时长，新增景点当前使用90分钟系统参考初值，不额外调用模型。程序根据顺序和所选交通推算，时长或路线未知则状态不完整。超出仍保留活动并明确标为参考冲突，不静默截断、删减或缩短时长。初次整份生成仍沿用“无已核实景点不能交付”的底线；编辑后删除全部景点可保留空行程日期，这是两种不同场景。

新增景点在当前天所有插入位置评估，原景点相对顺序不变；新路段各取最快可用方式，未变路段保留选择。优先已知不冲突的位置，再比较新增预计交通耗时；未知不当0、不宣称最优。若全部可能超时仍选参考成本较低的位置保留新增项并提示。成本相同保持稳定的靠前插入位置。空日直接加入。用餐区域需要时在当天重推荐，用户明确指定餐厅不替换。

路线缓存使用有方向的地点身份、方式和相关出发日期/时段；接口支持时间参数时传递，否则注明为查询时参考。后续出发时间变化时仅对受影响的时间相关缓存重查，设查询与迭代上限，避免无限逼近实时交通。地图仅展示路线参考，不引入停车、租车可用性、车辆追踪或班次保障。

### 3.4 编辑接口与并发

保留 `POST /api/trip/tasks`、状态与结果轮询，服务端存储原始生成结果。实际采用 `POST /api/trip/recalculate-day`，参数为task_id、date、edit_token、client_revision、request_id及最多20项有序operations：add_poi/delete_activity/move_activity/select_leg_mode。新增只传POI身份和临时activity_id，服务端核实并决定插入位置。

实际实现用签名日快照代替可任意改写的客户端草稿：签名绑定原任务、日期、当天内容和撤销的必去要求；服务端逐项应用操作，重算派生数据，返回目标日期与请求标识。其他天保持客户端当前结果，费用由前端汇总当前全部日期。费用、坐标、全局条件及原参考时长不能由客户端随意修改。

服务端不保存编辑会话，不覆盖原生成结果。签名密钥属于当前进程，重启需重新载入原行程；原任务被清理返回明确错误。过大快照仍允许阅读与导出，明确提示不可继续编辑。删除必去地点的撤销状态随签名快照保留，不影响其他要求。该方案的取舍见主目录学习日志。

复用 `GET /api/map/poi` 搜索，补充 `GET /api/map/poi/{poi_id}` 详情。同步地图调用离开事件循环，使用现有超时机制；编辑请求设置总耗时和查询额度上限，不降低120秒axios超时。超限返回明确错误或已知部分，不能假装完整成功。当前单进程中对地图/模型外部调用统一限制并发，缓存与MCP会话避免跨请求共享可变状态。

前端工程默认去抖400ms，同一天最多一个执行中的重算，积累后续有序操作并在结束后分批提交；切换交通同样适用。以日期＋revision＋request_id核对响应，旧响应不得覆盖新状态或切换后的地图。删除确认取消不发请求。同天重复POI前后端双重拒绝，跨日只提示。

编辑立即显示最新列表，受影响路段及后续时间标记updating；失败改failed/unknown并提供重试，不回滚用户列表、不残留旧耗时。未变且仍有效的数据可以保留。无有效路线属于信息缺失，可带提示交付；服务异常属于更新失败，两者区别展示。

### 3.5 数据接入与费用

使用现有高德适配边界，核查MCP是否支持骑行、详情字段及出发时间参数，不足时补充后端官方HTTP适配，不将服务端Key暴露到浏览器。不调用付费API、无免费额度时停止相关查询并说明缺失。单任务额度与账号免费额度分别管理，不能假设其他应用不消耗同账号额度。

保留资料来源用于排查，页面只需简洁的“参考价格”。消费必须来自查询；模型可以解释和推荐，但不能写入数值价格。餐饮区域没有具体消费不补均价；住宿没有可用价格就缺失。已知项目不足时小计标“不完整”，已知部分超过目标可提示“已知参考费用已超过预算”；不能把小计低于预算解释为达标。当前适配仅汇总明确数值和可解释单位；无法解析的区间或单位保持缺失，不擅自取中间值。

初次开放和天气供模型参考；编辑后用已有/刷新数据生成提示，不自动换景点。返回缺失值，前端用一致文案，不把API失败、没有数据和免费混淆。

已有免费MCP小样本验证步行、骑行及公共交通无路线处理，不能据此推断全面覆盖；参考文档：[高德路线](https://lbs.amap.com/api/webservice/guide/api/direction)、[POI](https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch)、[天气](https://developer.amap.com/api/webservice/guide/api/weatherinfo)、[配额](https://lbs.amap.com/pages/base_service_price)。免费真实价格覆盖不足是接受的缺失状态，不以模型补价解决。

### 3.6 图片导出

新增独立导出组件，以按钮点击时当前展示数据的深拷贝为输入，展开全部日期，包括空日、更新中/失败、未知及可能超时提示。生成过程中冻结这份展示快照，后续编辑不修改正在渲染的图片。此快照是当前可见数据，不是上一份计算成功的结果。

复用已安装html2canvas，固定宽度布局，等待字体和图片，失败图片使用占位；不依赖当前选中的日签、不复制地图WebGL canvas。内容高度超出安全尺寸按日期拆分，单日再按活动块拆分。只处理图片技术错误和重试，不增加规划业务校验或禁用条件。

浏览器画布与跨域图片限制见[html2canvas FAQ](https://html2canvas.hertzen.com/faq)。实施需实测移动端和长行程，不照搬某浏览器理论最大尺寸作为所有平台保证。
