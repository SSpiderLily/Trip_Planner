## 问题 004：CHG-002 的规划与编辑规则不一致

### 目标与原因

旧结果以整日交通偏好、固定时间预算和模型估价组织内容，无法正确处理首尾到离时间、单段交通选择、局部编辑及查询数据缺失。新规则以景点推荐和路线参考为目标，不查询城际班次，不新增付费数据服务，也不提供导航。

### 取舍与实现位置

使用规则与接口入口见 [README](../README.md)，业务定义见 [CONTEXT](../CONTEXT.md)，此处不重复维护功能规格。

- 为保留原任务结果、避免新增编辑存储，采用签名日快照和有序操作。客户端不能伪造价格或全局条件；代价是服务重启后需要重新载入原行程，编辑不保证跨设备恢复。实现见 [day_edit_service.py](../backend/app/services/day_edit_service.py)。
- 查询事实与模型建议分离；未知时刻、费用不变成零，已知小计也不冒充完整结果。计算集中在 [schedule_service.py](../backend/app/services/schedule_service.py)、[cost_service.py](../backend/app/services/cost_service.py) 和 [route_options_service.py](../backend/app/services/route_options_service.py)。
- 编辑中的列表和已接受的计算结果分开管理，失败不撤销用户操作；导出冻结当前展示，不以重算成功作为前置条件。实现见 [RouteResultEditable.vue](../frontend/src/views/RouteResultEditable.vue) 和 [TripImageExport.vue](../frontend/src/views/TripImageExport.vue)。

### 调试中发现并修正的问题

1. `value or fallback` 会把真实价格0当作空值，改为明确判断 `None`。
2. 未知路段曾导致后续已知时长不再计入总量，改为将时刻推算与已知总量分开。
3. 高德骑行工具名称及参数与步行接口不同，按实际MCP定义适配；POI搜索没有坐标时通过详情补全，图片对象归一化为地址列表。
4. `uvx` 不在当前PATH和缓存权限不足会让MCP发现返回空工具。支持已安装的 `~/.local/bin/uvx`，并拒绝将空工具集合记录为初始化成功。
5. 导出分页不能重新按原页面选择器解析已经拆散的节点，否则可能遗漏长提示；按保留的内容块分页并校验尺寸。38,000字压力测试还发现选择器先命中短地址、未拆长简介，改为选择最长文本块；更新失败或进行中时，同时隐藏旧活动时刻。
6. 失败新增再删除不能继续重试该新增；折叠未提交操作时还须补偿排序，否则移除临时景点会改变其他景点最终顺序。

## 问题 001：Vite 类型环境缺失

### 1. 目标

让 TypeScript 正确识别 Vite 提供的客户端类型，并减少当前前端构建错误。

### 2. 错误现象

执行：

```bash
cd frontend
npm run build
```

关键报错包括：

```text
Cannot find module 'ant-design-vue/dist/reset.css' or its corresponding type declarations.
Property 'env' does not exist on type 'ImportMeta'.
```

同一次构建还暴露了日期字段类型冲突和未使用函数；它们不属于 Vite 类型环境问题，已在对应组件中一并修复。

### 3. 原因分析

`tsconfig.json` 只包含项目源码，并不会自动让 TypeScript 加载 Vite 的客户端全局声明。

Vite 的 `vite/client` 声明文件提供两类项目需要的环境类型：

- `declare module '*.css'`，使 `import 'ant-design-vue/dist/reset.css'` 成为合法的副作用导入；
- `ImportMeta` 与 `ImportMetaEnv`，使 `import.meta.env.VITE_*` 可以通过类型检查。

项目启用了 `noUncheckedSideEffectImports`，因此缺少 CSS 声明时会直接报 `TS2307`；缺少 `ImportMeta` 扩展时会报 `TS2339`。

### 4. 尝试过的方案

未采用在每个组件中手写 `declare module '*.css'` 或把 `import.meta` 强制转换为 `any` 的方式。前者会重复维护声明，后者会失去环境变量的自动补全和类型检查。

### 5. 最终解决方案

新增 `frontend/src/vite-env.d.ts`：

```ts
/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_API_BASE_URL?: string
  readonly VITE_AMAP_WEB_JS_KEY: string
}
```

三斜线指令会让 TypeScript 加载 Vite 的客户端声明；同名接口会通过声明合并补充本项目的 `VITE_*` 变量。`ImportMeta` 中的 `env` 字段由 `vite/client` 提供，本项目的声明只约束具体变量。

### 6. 验证方法

在 `frontend` 目录执行：

```bash
npm run build
```

实际结果：`vue-tsc && vite build` 通过，CSS 导入和 `import.meta.env` 的类型错误均已消除。

附带修复：日期选择器使用 `Dayjs | null`，API 请求使用 `YYYY-MM-DD` 字符串。表单状态通过 `Omit<TripFormData, 'start_date' | 'end_date'>` 替换日期字段类型，并在提交时调用 `format()` 转换，避免交叉类型产生错误的 `string & Dayjs`。

### 7. 注意事项

`VITE_*` 变量在 Vite 构建时注入前端代码，不应放置任何服务器端密钥。`VITE_AMAP_WEB_JS_KEY` 是浏览器使用的高德 Web 端 JS Key，与后端的 `AMAP_API_KEY` 不同。

类型声明只能帮助开发阶段发现拼写和使用错误，不能证明变量在运行时已配置。因此地图初始化额外检查空值和 `your_` 占位符，并提示用户在 `frontend/.env` 中配置后重启前端服务。

### 8. 学习总结

遇到 `import.meta.env` 或 CSS 导入的类型错误时，先检查项目是否存在并被 `tsconfig.json` 包含的 `vite-env.d.ts`，再确认其中包含 `/// <reference types="vite/client" />`。随后只为项目实际使用的 `VITE_*` 变量补充类型，并在依赖配置的功能入口增加运行时校验。

## 问题 002：旅行规划健康检查读取不存在的 Agent 属性

### 1. 目标

让 `/api/trip/health` 按当前四 Agent 规划器结构返回健康信息，并避免首次初始化阻塞 FastAPI 事件循环。

### 2. 错误现象

健康检查把 `get_trip_planner_agent()` 的返回值当作单 Agent 包装对象，读取 `agent.agent.name` 和 `agent.agent.list_tools()`。实际返回的是 `MultiAgentTripPlanner`，它没有 `agent` 属性，因此成功初始化的规划器也会让健康检查进入异常分支并返回 503。

### 3. 原因分析

当前规划器分别持有景点、天气、酒店和行程规划四个 `SimpleAgent`，并把 `get_expanded_tools()` 得到的高德工具列表保存在 `amap_tools`。健康路由仍沿用旧的单 Agent 对象结构。

此外，首次调用 `get_trip_planner_agent()` 会同步创建 LLM 与 MCP 工具；如果直接在异步路由中调用，会占用事件循环线程。

### 4. 尝试过的方案

没有给规划器添加兼容用的 `agent` 属性，因为这会掩盖实际的多 Agent 结构，也无法准确代表工具数。

### 5. 最终解决方案

健康路由在线程池中调用 `get_trip_planner_agent()`，保留原有初始化异常到 HTTP 503 的映射。健康响应保留 `status`、`service`、`agent_name` 和 `tools_count`：`agent_name` 明确标为“多智能体旅行规划系统”，`tools_count` 使用 `len(planner.amap_tools)`；新增 `agents` 列表返回四个 `SimpleAgent.name`。

### 6. 验证方法

在 `backend` 目录执行：

```bash
venv/bin/python -m unittest tests/test_trip_health.py tests/test_trip_planner_agent.py
```

实际结果：3 个测试通过。使用不含 `agent` 属性的替代规划器验证健康响应结构和工具数，并模拟初始化异常验证 503 响应；同时现有的 MCP 工具注册测试通过。

### 7. 注意事项

该端点报告规划器初始化和已发现工具的数量，不代表每个 LLM 或高德 MCP 请求都能成功完成。

### 8. 学习总结

健康检查应读取当前服务对象的真实结构；多 Agent 系统应分别报告系统名称、成员 Agent 和共享/发现工具数量。异步路由调用可能阻塞的同步初始化函数时，应把初始化放入线程池。

## 问题 003：本地启动前后端需要两个终端

### 1. 目标

从项目根目录用一条命令启动本地前后端，并在退出时一起停止。

### 2. 错误现象

之前需要在两个 VS Code 终端分别进入 `backend`、`frontend`，激活后端虚拟环境并执行启动命令；停止时也要逐个结束。

### 3. 原因分析

后端依赖项目内 `backend/venv`，前端依赖 `frontend/node_modules`，两套开发服务都是长期运行的进程。普通的顺序命令会在第一个服务处等待，无法启动第二个。

### 4. 尝试过的方案

没有改动 `backend/run.py` 或前端 npm 脚本；根目录脚本直接调用各自现有的运行程序，避免改变单独启动方式。

### 5. 最终解决方案

新增根目录 `dev.py`：检查本地依赖，分别在各自目录启动 Uvicorn 与 Vite，监视进程退出，并在 `Ctrl+C` 或某一服务退出时停止两个进程组。后端绑定 `127.0.0.1:8000`，前端绑定 `127.0.0.1:5173` 且端口占用时直接失败。为使后端导入错误立即结束服务，后端不启用 Uvicorn 重载；修改后端代码后需重启脚本。若 Mac 通过 Rosetta 运行根目录 Python，脚本会检查并在可用时以 arm64 启动现有虚拟环境。

README 增加一键启动说明。脚本只提示 `.env` 是否存在，不打印密钥内容。

### 6. 验证方法

从根目录运行 `python3 dev.py`，访问前端与后端健康端点，再用 `Ctrl+C` 检查两项服务是否退出；用 `ast.parse` 检查脚本语法，运行 `git diff --check`。

实际结果：自动验证时，Vite `http://127.0.0.1:5173/` 与后端 `http://127.0.0.1:8000/health` 均返回 HTTP 200；`Ctrl+C` 后两个地址均无法连接，脚本退出码为 130。语法与差异格式检查通过。随后用户在本地使用脚本成功启动项目并生成了行程结果。这证明一键启动及前后端基本请求链路可用；本次未核查该请求的模型和高德 MCP 调用记录，也未确认结果是否来自备用行程。

首次沙箱内启动因本地监听权限失败；获准在沙箱外启动后发现该运行环境以 x86_64 启动双架构 Python，而现有 `pydantic_core` 为 arm64。脚本增加 arm64 导入探测后，后端成功启动。为避免重载父进程掩盖工作进程导入错误，脚本默认不启用后端重载。

用户最初在非项目根目录运行 `python3 dev.py` 时收到“找不到 dev.py”；这与虚拟环境位于 `backend/venv` 无关。使用脚本的绝对路径或先切换到项目根目录即可。

### 7. 注意事项

此脚本用于 Mac/Linux 的本地开发，需要先安装两端依赖。服务日志仍直接显示在同一终端；真实旅行规划还需要后端密钥和 `uvx`。

### 8. 学习总结

本地开发启动器可以直接调用虚拟环境中的 Python，无需先执行 `activate`；进程管理需要同时处理正常退出、启动失败和手动中断。

## 问题 006：MCP 子进程找不到 uvx

### 原因与修改

MCP 工具启动时使用显式环境变量，子进程可能无法从 `PATH` 找到 `uvx`，导致地图工具发现失败。启动命令现在优先使用当前 Python 旁边可执行的 `uvx`，再检查 `~/.local/bin/uvx`，最后查询 `PATH`；均不存在时明确报错，不将空工具集合当成成功。

### 验证记录

模拟 `PATH` 无 `uvx` 且虚拟环境中无 `uvx` 的场景，确认使用本地可执行文件；后端 84 项 unittest 全部通过（含 MCP 工具注册测试）。此测试不替代用户本地启动后对真实高德服务的验收。
