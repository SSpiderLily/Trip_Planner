# 旅行规划体验优化需求

更新日期：2026-09-27

状态：最小闭环已通过本地验收；下述完整目标仍分步落实。

## 推进原则

优先跑通可验证的最小完整流程，停止逐字段、逐个常规实现选择的确认。已确认需求作为目标分步落实；其余字段、对象关联和常规技术细节由实现时按最简可用方案确定，通过实际运行发现问题后修正，不以契约细节尚未穷尽为由阻塞实现。未确认的字段建议不作为既定需求。保留基本校验与已有明确约束，尤其禁止用机械规则识别用户开放意图。

本文是本轮优化的唯一需求依据，只记录用户体验目标与边界。当前已实现的业务规则见 [CONTEXT.md](../CONTEXT.md)。不在本文维护技术实现或重复执行进度；优化完成并验收后，将必要的使用说明与稳定规则归入 README、CONTEXT.md，再删除本文并清理入口。

## 目标与重点（已确认）

用户尽量少填信息，即可获得每天去哪玩、吃什么、怎样走更顺的旅行安排。结果页以住宿为路线基点，重点展示每日游玩、用餐与合理路线。

- 优先解决完整游玩日的安排；首尾日到达、离开等细节不作为本轮核心，不要求用户额外填写。
- 同一天的景点尽量集中、减少折返，用餐顺路，每天内容适量。
- 已有住处时围绕它安排；没有住处时，先安排景点，再综合多日路线推荐一个住宿区域，默认全程不换住处。不默认推荐具体酒店，明确标注区域参考点及交通估算依据。

## 用户输入（已确认）

| 信息 | 必填性与交互 | 用途或默认行为 |
| --- | --- | --- |
| 目的地 | 必填，城市搜索选择 | 确定规划范围 |
| 出行日期 | 必填，起止日期选择 | 自动计算天数，不再单独填写天数 |
| 已定住处 | 选填，搜索酒店或地点 | 未填时推荐住宿区域 |
| 游玩偏好 | 选填，多选标签 | 如自然风光、历史文化、美食、城市漫步；未填时综合安排当地特色 |
| 其他要求 | 选填，自由文本 | 可描述老人孩子、轻松节奏、自驾、必去景点、预算限制等 |

选填项收在“更多偏好”中。默认按普通成人、适中节奏、公共交通结合步行规划；提交前用一句话展示默认安排，允许通过“其他要求”调整。交通方式、住宿档次不再要求单独填写。

本轮对“带老人、带孩子、少走路”等描述只附出行提醒，不自动调整默认路线，也不追问年龄等信息；页面须明确说明未据此调整，不能宣称满足相应需求。

## 规划规则（已确认）

- **景点依据**：正式路线只包含已核实景点（定义见 [CONTEXT.md](../CONTEXT.md)）。名称和位置取自地图查询结果，模型负责选择、排序和推荐理由；开放时间、价格与预约条件允许未知并提示。
- **内容与节奏**：按游览和交通耗时安排，上午、下午各有主要活动，不固定景点数量。优先匹配偏好，兼顾当地代表性与路线顺畅，不要求偏好平均分配。
- **时间检查**：每日时间预算默认 10 小时，覆盖从住宿基点出发到返回的游览、午晚餐、交通、自由活动及缓冲；这是上限，不要求排满，可选夜游另计。由程序合计并检查，超限触发调整；模型可提供游览等时长估计，但不独自判定是否过满。缺失耗时不按零计算，信息不足须提示，不能标为检查通过。无需新增用户必填项，默认值后续可根据实际路线评估调整。术语见 [CONTEXT.md](../CONTEXT.md)。
- **景点取舍**：默认优先顺路，可舍弃较远的热门景点。不同天尽量不重复同一景点；住宿、用餐区域和交通枢纽可重复，用户明确要求重游时例外。
- **必去景点**：保留全部需求及其处理结果。已核实的必去景点保留安排；时间过紧时提醒，超过可用时间或与开放条件冲突时标出具体问题，不能标为可直接执行。查不到或无法唯一定位的地点放入“未能安排的必去地点”，说明原因、不放入正式路线，其他已核实景点继续规划。普通推荐景点可替换或减少。
- **餐饮与夜游**：默认安排午餐、晚餐，推荐当地特色食物和顺路用餐区域，有可靠信息时附具体餐厅。早餐按需推荐；有合适且顺路的晚间活动时作为可选项，不强行填满。
- **用餐区域定位**：未选具体餐厅时，使用地图查询得到的区域参考点参与路线计算并明确标注；提示实际餐厅位置可能增加步行，不将参考点展示为已选餐厅。区域参考点术语与住宿区域共用，见 [CONTEXT.md](../CONTEXT.md)。
- **交通**：默认公共交通结合步行，明显不便的路段附打车选项。对最终选定的路线查询地图服务，查不到时标记估算或未知。
- **路线调整**：交通查询发现绕路或安排过满时，自动调整顺序、跨天分配或调整普通景点，再检查路线；已核实的必去景点保留，未解决的冲突展示给用户。初稿检查后最多自动调整 2 轮，每轮调整后重新检查路线、时间及预算；没有待调整问题时提前结束。达到上限仍有问题，交付满足最低条件的行程并标明冲突；不满足最低条件时判定失败。
- **开放与预约**：尽量查询并参与安排；信息缺失标记待确认，已知闭馆时调整日期。必去景点全程不可游览时保留其信息并标出冲突。
- **天气**：有对应日期预报时，尽量将室内活动安排在雨天、室外活动安排在其他天；必去景点保留，无法调整时提醒。预报未覆盖时正常规划并标记天气未知。
- **天气查询失败**：允许继续规划，页面明确提示查询失败且未根据天气调整；观测保留工具调用失败记录。最终满足最低交付条件且保存成功时，任务仍为生成完成，不把查询失败改记为预报日期未覆盖。
- **候选不足**：使用已有可靠景点，保留自由活动时段并说明原因，不靠重复景点或增加远距离通勤填满天数。
- **自由活动定位**：未指定地点时默认在上一活动附近进行，只预留时间、不新增地图节点；后续交通从上一已定位地点计算，并注明未包含用户自行离开该区域的路程。
- **自由活动结构**：沿用统一活动结构，保留活动 ID、类型、时段、说明和时长；没有具体地点时 `place` 为 `null`，参与时间合计，但不生成额外地图节点。后续路段按上一已定位地点计算，不将无地点活动当成可查询的交通端点。
- **可选夜游路线**：主路线默认晚餐后直接返回住宿基点；夜游单独提供“晚餐地点 → 夜游地点 → 住宿基点”的替代路线，分别展示耗时。选择夜游时替换原晚餐后返程路段，不将两条返程同时计入时间或费用。替代路线不改变基础路线的每日时间预算检查。

## 费用口径（已确认）

- 默认展示每天和全程预计总费用，按每位成人计算，包含门票、餐饮、市内交通；住宿另列参考，不含往返目的地的大交通。
- 注明估算依据，区分查询价格与估算。未知费用不按零计算，无法覆盖的费用须注明，避免将已知部分误称完整总价。
- 可选夜游不计入基础总费用，另列额外费用。
- 夜游额外费用按替代路线与基础路线的费用差额计算，包含夜游活动费用及交通变化，不重复计算原返程；费用缺失时明确提示，不能按零补齐后给出确定差额。
- 自由文本只写“预算 2000 元”等未注明口径时，沿用上述每位成人全程游玩费用口径，并展示理解结果；明确说明其他口径时按用户要求处理。
- 超预算时优先调整普通景点、餐饮和交通，保留必去景点；仍超预算则展示差额与原因。

## 结果页（已确认）

- **默认布局**：当天路线详情与地图为主体，顶部切换日期；住宿区域和多日概览放在简短摘要中。
- **每日安排**：展示游览顺序、景点推荐理由与建议停留时长，以及顺路的当地特色饮食与用餐区域。
- **统一活动顺序**：每日使用一份有序活动列表，景点、用餐和自由活动穿插排列；上午、下午等作为活动时段标签。规划、交通计算、地图与页面共用该顺序，前端不再自行拼接独立的景点和餐饮列表。活动概念见 [CONTEXT.md](../CONTEXT.md)。
- **路线地图**：按天与每日安排联动，展示住宿基点、当天景点、用餐地点或区域和游览顺序。
- **路段交通**：展示下一站的交通方式与预计耗时，帮助用户理解当天的交通负担；区域基点对应的估算应明确标识。
- **独立路段**：两地间的移动单独记录起点、终点、交通方式、预计耗时及查询或估算依据；无法取得耗时时保持未知。包括住宿基点到首个地点、最后一个地点返回住宿基点的交通，页面将路段与活动按顺序穿插展示。
- **住宿建议**：未提供住处时推荐住宿区域，简短说明它为何适合这几天的路线。
- 优先使用上午、午餐、下午、晚餐等时段组织，不要求精确到分钟，保留自由活动空间。
- 预约、开放限制等需要时单独标注具体时间。天气、预算和详细景点介绍作为辅助信息，页面主体保持路线容易阅读。
- **问题展示**：顶部汇总冲突与待确认事项，具体问题标在对应地点或路段；点击汇总可定位，并区分已知冲突与信息缺失。
- **问题数据**：使用结构化问题列表，逐项记录问题类型、影响范围、说明及相关日期、活动或路段；允许整份行程层面的问题。程序从该列表汇总“需调整”“有待确认事项”，修改 Agent 与前端使用同一份记录，不分别从自由文本推断问题。
- **未能安排的必去地点**：单独列出原始地点需求及未安排原因，作为未满足的要求提示需调整，不为其编造地图节点。
- **修改范围**：本轮不新增局部编辑与自动重规划，用户调整输入后重新生成整份行程。现有前端本地编辑功能如何衔接，留待技术设计处理。

## 最低交付条件与结果提示（已确认）

- 至少有一条包含已核实景点、游览顺序与住宿基点的日路线，允许交付；餐饮、交通或部分天数的信息不足明确提示，缺少安排的时段保留自由活动。
- 用户指定的住处无法定位时，作为住宿基点可计算要求的明确例外：保留原输入并提示无法定位，不擅自改选住宿区域；展示已核实地点间的路线，往返住处的交通标记未知，不编造坐标，也不要求用户重新选择后才生成。未知的往返耗时不按零计入每日检查，不能据此断言整天安排可行。
- 完全没有已核实景点时判定规划失败，不构造占位行程。交付条件不免除输入日期和行程日期一致等现有要求。
- 区分可用行程与需注意的行程：已知时间冲突、超预算、部分天数缺少安排时提示“需调整”；开放时间等信息缺失时提示“有待确认事项”。两类提示可以同时存在。
- 任务成功状态沿用 `succeeded`，页面含义为“生成完成”：满足最低交付条件的行程已生成并保存。行程问题独立表达，允许“需调整”和“有待确认事项”同时存在，不新增“部分成功”任务状态。领域术语见 [CONTEXT.md](../CONTEXT.md)。

## 验收方向

- 只填写目的地与日期即可提交规划；选填内容按上述支持范围参与安排或产生明确提醒。
- 有住处和无住处两种情况都能形成有明确住宿基点的每日路线。
- 用户能从结果页直接看懂每天去哪玩、吃什么、按什么顺序走和大致交通耗时。
- 用实际生成的行程核对地点是否集中、用餐是否顺路、安排是否过满；具体检查标准在技术设计时细化。
- 验证必去景点冲突、超预算、路线查询缺失、候选不足、完全无可靠景点等场景，交付与提示符合上述规则。
- 每日与全程费用口径一致，可选费用单列；已知冲突、待确认信息和任务失败不会混为一种状态。

## 后续设计边界

### 已确认的流程控制

额外要求作为完整备注原样保留，开放意图由模型理解。严禁用关键词匹配、正则、硬编码分支或规则词典从自由文本推断必去地点、预算、同行人群等用户意图，也不得在模型理解失败时用此类逻辑兜底。需要供程序检查的规划条件，由模型理解后输出，三个 Agent 共用同一份理解结果及用户原文，不各自独立解释约束。程序只负责结构与类型校验、显式日期计算、金额比较、已明确地点的关联检查等确定性处理，不能据此宣称已验证模型对原文的理解正确。不得丢弃未被结构化表达的原始要求。“带老人、带孩子、少走路”等按已确认范围仅生成提醒；理解工作由候选搜集 Agent 在首次搜索前承担，具体字段范围待细化。术语见 [CONTEXT.md](../CONTEXT.md)。

由程序控制搜集地点、生成安排、查询交通、检查与调整等阶段的推进，保证地点核实、必要检查和调整次数上限被执行。模型负责阶段内的选择与安排，包括景点选择、活动排序和根据检查问题修改行程；不由自主 Agent 决定是否跳过检查或何时无限继续。具体角色划分见下节。

### 已确认的角色划分

采用多个专业 Agent，分别负责候选搜集、行程安排和修改。程序仍负责阶段推进、工具结果核实与规则检查，角色拆分不改变必需检查和最多 2 轮调整的限制。

候选搜集 Agent 在首次搜索前结合显式表单与完整额外备注理解需求，先输出统一规划条件，再据此开始查询。行程安排与修改角色接收同一份规划条件及原文；不新增独立需求理解角色或单独的前置需求理解模型调用。程序不得用规则替代开放意图理解，模型交互的具体实现按该阶段职责设计。

备注与明确表单输入的语义冲突由模型识别：以明确表单项为准继续规划，并展示冲突说明；备注可以补充要求或调整默认值，不直接改写已选城市、日期等明确输入。程序可以检查输出是否保持显式表单值，但不能据此推断原文是否存在语义冲突。领域规则见 [CONTEXT.md](../CONTEXT.md)。

各 Agent 使用独立上下文，通过结构化数据交接，不共享本次规划的完整对话历史。每次调用由程序提供该阶段所需的信息；例如修改 Agent 接收用户需求、当前行程、已核实候选及检查问题。具体交接字段与校验方式在技术设计中细化。

活动与路段各自携带完整地点信息，不采用只引用内部地点 ID、展示时再查地点表的结构。程序保留原始查询结果，逐项核对地点身份、名称和坐标，并检查同一地点在不同活动、路段中重复出现时的信息一致性。完整携带不代表允许模型改写查询事实，无法对应已核实地点的内容不得进入正式路线。具体来源标识与字段在数据设计中确定。

地点身份能明确对应原始查询记录时，程序用查询值统一修正名称与坐标，并在修正后计算路线；不因可确定修正的转述或抄写差异直接拒绝整个结果。无法明确对应查询记录时拒绝该结果，不凭近似名称猜测替换地点；修改阶段按无效修改规则保留上一份有效行程。

候选搜集 Agent 可以根据查询结果调整搜索条件并继续补充查询；程序限定可调用工具和调用次数、负责工具执行与保留原始地点数据。Agent 决定搜索内容及是否需要补充，但不能绕过程序限制。具体调用上限待技术设计确定。

一次规划共享地点查询总额度，景点、住宿区域和用餐区域等阶段另设上限，并为后续阶段预留额度。重复调用搜集 Agent 不重置总额度；具体数值可配置，通过实际调用测试调整。该额度针对地点查询，天气及路线查询的限制另行设计，不混用计数。

单次地点查询超时或报错时，记录该次失败、保留已有候选，在剩余总额度和阶段额度内允许继续搜集；失败调用同样消耗额度，不因失败自动重置额度或无限重试。局部查询失败不直接判定整份规划失败，最终仍按最低交付条件判断。

候选搜集 Agent 统一负责景点、用餐区域和住宿区域的地点查询，由程序分阶段调用：先搜景点，形成初步游玩分布后，再按需搜集住宿区域与沿途用餐区域。搜集角色提供候选，行程安排 Agent 负责组合行程；天气和交通查询由程序负责，不交给行程安排 Agent 自行查询。

修改 Agent 只能使用已搜集并核实的候选，不直接查询地点，也不请求候选搜集 Agent 补充搜索。无法解决的问题通过减少普通景点、保留自由活动或明确展示冲突处理；已核实的必去景点继续保留。程序仍须对修改后的路线重新查询、检查交通，这不属于补充地点搜索。

用户指定的住处固定，不在自动调整中替换。系统推荐的住宿区域可在已搜集并核实的候选中调整，不新增地点搜索；最终仍只推荐一个住宿区域，调整后由程序重新计算受影响的各天往返交通，并重新检查时间与费用。

修改 Agent 返回修改后的完整行程，不输出局部修改指令。程序统一校验日期、地点引用、必去景点保留情况和活动顺序，再更新路线与费用；模型返回的名称、坐标和费用合计不能绕过已有事实来源与计算规则。具体字段在技术设计中确定。

初稿出现非法 JSON、缺少必需字段等结构错误时，允许将校验错误反馈给行程安排 Agent，进行一次结构修复，不新增地点搜索；修复后仍不合法则任务失败，不交付无效结果。该次结构修复与后续最多 2 轮行程优化分别计数，不构成对任意工具或网络故障的通用重试。结构修复成功后仍须执行地点、日期及其他业务校验，不能仅凭格式正确交付。

已有满足最低交付条件的有效行程时，修改结果若为非法 JSON、引用不存在的地点等校验不通过，拒绝该次修改、不覆盖上一份有效行程。失败尝试计入最多 2 轮的限制；有剩余轮次时反馈错误继续调整，轮次用完则交付上一份有效行程，保留原有问题并提示调整未完成，观测记录失败尝试。此规则保留的是经校验的真实结果，不允许构造占位备用行程。

修改后的行程即使结构合法，仍须比较修改前后的检查结果；引入新的已知安排冲突时不接受该版本，例如解决超时却把景点移到闭馆日。保留上一份有效行程，反馈新增冲突；该次尝试计入 2 轮上限，有剩余轮次时继续调整。不能仅因是最新版本就覆盖已有结果。

### 已确认的历史结果处理

历史行程不迁移为新结构，也不提供旧格式的完整结果页适配；保留原始数据查看。新结果页仅展示新结构行程，旧任务须有明确的旧格式提示与原始数据入口，不能因格式不同而显示为生成失败。需要新版体验时重新生成；本决策不授权删除现有历史数据，既有保留期规则不变。

### 已确认的存储方案

沿用 `tasks`、`task_results`、`spans` 三张表，暂不新增旅行业务表。一个任务对应零或一份最终结果及多个 Span：`tasks` 保存原始请求和执行状态，`task_results.result_data` 保存完整行程 JSON，`spans` 保存执行观测。

九类业务对象在结果 JSON 中组织：规划条件保存本次实际采用的需求及默认值；行程包含住宿基点、每日安排、费用汇总和问题列表；每日安排包含活动与路段，完整地点信息嵌入相关对象，费用明细附于活动和路段。原始请求与解析后的规划条件分别保留，不混为一份数据。

结果增加格式版本标识，区分新旧结构；不将无版本的旧结果解释为新结构。保存前由业务模型和程序检查日期、引用、地点事实、汇总及最低交付条件，数据库保证任务归属、唯一性和事务。最终结果保存与任务标为 `succeeded` 继续在同一次事务中完成。仅在以后出现独立编辑、版本管理或跨行程查询等明确需求时重新评估拆表。

### 已确认的行程外层契约

最终行程包含 `schema_version`（格式版本）、`planning_conditions`（统一规划条件）、`lodging_base`（住宿基点）、`days`（按日期排列的每日安排）、`cost_summary`（全程费用汇总）及 `issues`（统一问题列表）。天气信息放入对应的每日安排；未安排的必去地点通过规划条件中的要求及关联问题表达。任务执行状态继续由任务接口提供，“需调整”“有待确认事项”由问题列表汇总，不另由模型生成独立结论。

### 已确认的住宿基点契约

`lodging_base` 使用统一结构，`source` 区分 `user`（用户提供）与 `recommended`（系统推荐）；`place` 保存完整的已核实地点，用户住处无法定位时为 `null`，并保留原始住处描述、关联定位问题。系统推荐时保留区域名称、推荐理由和已核实区域参考点。程序依据来源执行既定调整规则：用户住处固定，推荐区域可在已有候选中调整，不另存可与来源矛盾的调整权限字段。

字段采用 `source`、`user_input`、`area_name`、`recommendation_reason`、`place`。系统推荐时 `user_input` 为 `null`；用户提供时不适用的区域和推荐理由为 `null`。推荐来源须具备区域、理由和已核实参考点；定位失败等问题只记录在行程统一 `issues` 中，不在住宿对象重复维护错误状态。

### 已确认的每日安排契约

每日安排包含 `date`、`description`、`activities`、`legs`、`optional_plans`、`weather`、`time_summary`、`cost_summary`。`description` 是 Agent 给出的一句简短安排说明，解释当天的组合或顺路依据，须对应最终路线，修改安排时同步更新。

`activities` 与 `legs` 表达基础活动及交通，包含往返住宿基点的路段；`optional_plans` 单独组织可选夜游及替代路线，避免重复合计。天气由程序整理查询结果；时间和费用由程序汇总，未知项不能按零补齐，已知部分合计不等于完整总量或检查通过。

每日日期完整、有序且与输入一致，候选不足时仍保留该日，以自由活动及关联问题说明。“第几天”按日期顺序计算，不另存 `day_index`。每日不重复保存问题列表，行程统一 `issues` 通过日期、活动或路段标识关联该日。

### 尚待细化的内容

尚未确定各 Agent 的具体输入输出字段、工具调用权限、查询策略及路线校验算法。自动调整上限见规划规则。观测页面优化另行讨论。每日主题标题并非已确认的必需输出。

最小版本已替换原固定景点、天气、酒店查询流程：天气和交通缺失允许带提示交付；没有已核实景点、日期不合法或无法形成有效结果时任务失败。完整目标与当前范围的差异见下节。

## 本轮实现范围与剩余工作

本轮优先实现简化输入、三角色工作流、真实地点核实、住宿基点、每日餐饮与活动、交通查询、时间/费用检查、最多两轮修改及新版结果页；继续复用任务与观测。具体实现以代码和测试为准。
