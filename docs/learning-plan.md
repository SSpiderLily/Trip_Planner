# HelloAgents 智能旅行助手学习计划

更新时间：2026-09-29

## 学习目标与范围

项目定位：以智能旅行助手为载体的全栈技术实践项目。目标是独立完成“需求与交互设计 → 前端页面 → API 与数据存储 → Agent 与外部服务 → 测试、观测与部署”的完整交付，并能跨层定位问题、验证改动效果。

- 前端：Vue 3、TypeScript、组件拆分、表单与状态管理、异步交互、地图展示、响应式布局与基本可访问性。
- 后端与数据：FastAPI、数据契约、SQLite、事务、配置管理、服务职责、异常与超时、同步与异步、测试。
- Agent：LLM 与工具调用、MCP、上下文、结构化输出、流程编排和效果评估，作为全栈产品的智能能力。
- 工程交付：Git、前后端联调、观测与排障、构建、Caddy、服务管理、自动部署与回滚。

以完整功能为学习单位，让前端、后端与 Agent 围绕同一用户需求协同推进，不固定时间比例。每个功能同时检查交互是否清楚、数据是否正确、失败是否可见、上线是否可复现；各阶段按验收结果推进，不设固定周数。

## 第一轮项目完成标准

目标：交付一个可部署、可实际使用、可持续维护的小型旅行规划产品，供自己和少量受邀使用者使用。以下是目标验收标准，尚未全部完成；学习阶段 1—5 服务于本轮交付。

| 维度 | 完成标准与证据 |
| --- | --- |
| 产品可用 | 从城市、日期与可选要求生成以住宿为基点的每日景点、餐饮和顺序；可看地图、按需交通方案、含住宿费用区间、进度、失败原因与历史结果。用几个真实需求完成端到端验收；地点有依据、未知信息明确，能辅助初步出行安排。具体功能规则只维护在[旅行规划需求](trip-planning-requirements.md) |
| 能独立开发 | 独立交付至少一个跨页面、接口、服务、数据与测试的小功能；能解释各层职责、模型与程序边界，以及重复请求、刷新和失败时的行为；亲手定位并修复一次真实故障 |
| 关键流程有测试 | 覆盖日期、住宿晚数和费用区间计算，非法输入与第三方超时，任务成功/失败/中断，以及提交、结果、交通查询与重试的浏览器流程；发布前可重复执行检查，主动制造错误能被发现，不以覆盖率数字代替有效验证 |
| 服务稳定运行 | 前端构建产物经 Caddy 提供，后端由服务管理工具或容器管理；HTTPS、同源 API、配置与持久数据位置明确。关闭 SSH、重启服务器后服务可恢复；有基本访问控制或调用额度保护，受邀使用边界与观测数据访问范围明确，能查日志与调用记录 |
| 更新与恢复可靠 | 自动测试、类型检查和构建，发布版本可追踪，更新保留数据与密钥；完成正常发布、失败发布处理、版本回退和数据库备份恢复演练；能用 Docker 在另一环境复现运行。代码回退与数据库恢复分别验证 |

以上五项有验收证据后，第一轮可以收尾。当前单活动任务限制允许保留并明确提示；复杂多用户体系、高并发、专业旅行顾问级规划质量不作为本轮完成条件。MySQL、ORM、Redis、消息队列留作有实际场景的第二轮扩展，React/Next.js 可通过后续小项目学习。

最终保留四类成果：可使用的部署版本、可重复的测试与发布流程、简洁的运行/排障/恢复说明、可解释的功能交付与故障处理记录。证据集中在[学习日志](learning-log.md)，实际用法归入 README；不另建重复验收文档。第一轮收尾不等于全部产品需求完成，尚未实现的独有需求继续保留在对应计划中。

## 掌握程度与技术范围

不要求精通所有技术。统一标准是：知道职责、能查文档接入、能根据证据排障、能解释取舍。允许借助 AI，但须能解释生成的代码和配置，并亲手验证；不以安装成功或跟着教程运行作为掌握标准。

| 技术 | 优先级与学习范围 | 可验收的掌握程度 |
| --- | --- | --- |
| Python | 当前：模块、类型、异常、依赖、虚拟环境、同步与异步 | 修改后端功能、调用外部 API、处理失败并写针对性测试；能读异常堆栈 |
| Node.js | 当前先学工具运行时：npm、脚本、锁文件、环境变量；服务端开发后置 | 能安装依赖、运行和构建前端、定位版本问题；知道浏览器、Node 与 Python 各运行什么 |
| Git | 当前：差异、暂存、提交、分支、远程、冲突、撤销 | 独立交付一个功能分支，解决简单冲突并安全撤销错误 |
| Linux | 当前：文件、权限、进程、端口、SSH、日志、服务管理 | 部署服务并定位权限、端口、进程和配置问题 |
| 计算机网络 | 当前：DNS、IP/端口、HTTP/HTTPS、CORS、反向代理、超时 | 解释一次请求完整路径，区分浏览器、代理、后端、第三方故障 |
| HTML + CSS | 当前：语义、表单、盒模型、Flex/Grid、响应式与基本可访问性 | 完成桌面与手机可用页面，修复布局、滚动与键盘操作问题 |
| JS + TS | 当前：模块、事件、Promise、async/await、类型、联合类型、空值 | 实现异步交互与错误处理，避免旧响应覆盖新选择 |
| Vue / React | 当前深入已有 Vue 的组件、状态、路由与生命周期；React 后置 | 完成表单到结果与重试的完整功能，能合理拆分组件 |
| Next.js | 后续：先有 React 基础，再学路由、服务端/客户端边界、渲染与部署 | 在小项目中完成页面、数据获取和部署，解释选用理由；不重写本项目作为前置条件 |
| MySQL | 先用 SQLite 学 SQL、约束、事务、索引；后续练独立数据库服务 | 完成小范围数据迁移、连接配置、备份恢复，并验证数据一致性 |
| Redis | 后续：有路线缓存或共享限流需求时学键、TTL、失效和故障处理 | 验证命中、过期、更新与不可用行为；清楚持久数据来源 |
| ORM | SQL 基础之后：模型、查询、关联、事务、迁移 | 完成 CRUD 和一次结构迁移，能查看 SQL、识别多余查询；不依赖 ORM 掩盖事务问题 |
| REST API | 当前：资源、方法、状态码、契约、校验、分页、幂等基础 | 实现接口并与页面联调，定义正常、非法输入及外部失败行为 |
| Docker | 手动部署之后：镜像、容器、Dockerfile、端口、网络、卷、Compose | 在另一环境按文档启动，更新容器不丢数据库与配置 |
| 消息队列 | 后续：出现独立 worker、排队或跨进程执行需求 | 理解确认、重试、重复消费与幂等，验证 worker 退出后的任务处理；不承诺天然只执行一次 |
| CI/CD | 手动发布之后：自动测试、构建、产物、凭据、部署门禁、健康检查、回滚 | 推送触发验证，满足发布条件才部署；能定位失败步骤、确认版本和恢复上一版 |
| 系统设计 | 全程：职责、数据流、状态、同步/异步、失败边界与取舍 | 画出当前架构，解释成功与失败路径，说明增加组件的实际收益与成本 |

补充必需能力：针对性业务测试、API 验证、前端类型检查和浏览器流程测试；能结合 Network、Console、日志与观测记录排障。理解认证与权限边界、输入校验、密钥管理、前端构建变量可见性及数据备份。

## 分阶段学习与验收

按结果推进，不固定周数。已有功能可作为练习材料，无需重复开发；新增中间件由实际场景驱动。以下是学习目标与验收门槛，具体操作以代码、README 和对应功能计划为准。

| 阶段 | 实践目标 | 验收门槛 |
| --- | --- | --- |
| 1. 理解开发与生产 | 追踪页面 → API → Agent/外部服务 → 数据库 → 页面；区分 Vite 开发服务、前端 dist 和 Python 后端运行环境 | 能解释 npm dev/build 的不同、构建时与运行时配置、请求地址和密钥应放何处；能在本地构建并查看产物 |
| 2. 完成可验证的小功能 | 用按需交通或费用区间串联 Vue/TS、Python、REST、SQL 和 Git；已有功能则复盘其实现 | 正常、加载、空数据、非法输入、外部失败都能说明与验证；类型检查、构建和相关测试通过，能根据记录定位一次故障 |
| 3. 手动生产部署 | 将已验证前端产物交给 Caddy，运行 Python 后端；明确同源 /api、HTTPS、systemd 与持久数据目录 | 浏览器访问和页面刷新正常；关闭 SSH 后服务继续，重启能恢复；能查日志并完成数据库备份恢复。核对当前单进程约束，不盲目增加 worker |
| 4. 可重复发布与容器化 | 先明确发布版本、配置/数据保留、健康检查和回滚；再用 Docker/Compose 复现运行环境 | 换环境可启动，更新不丢数据，故障可恢复上一版；理解容器部署与直接用 systemd 管理后端是不同运行方案。代码回退不自动等于数据库回退 |
| 5. CI/CD | 将已验证的测试、构建、发布步骤接入 GitHub Actions，限定生产发布触发条件 | 故意制造测试失败能阻止发布；成功发布可确认版本，部署失败可诊断和回滚，凭据与真实数据不进入仓库及产物 |
| 6. 按场景扩展 | 数据管理需要时练 MySQL + ORM；重复查询需要时练 Redis；任务独立执行需要时练消息队列 | 每次只引入一个必要能力，完成正常与故障验证，说明前后收益；实验可用隔离小样例，不强制改生产架构 |
| 7. 扩展技术选择 | 后续小项目学习 React → Next.js，按需补 Node 服务端 | 能交付并部署一个小应用，解释与 Vue + Python 方案的差异；不影响当前项目交付 |

阶段 1—5 完成后，按上文“第一轮项目完成标准”统一验收；阶段 6—7 不阻塞第一轮收尾。

Agent 学习持续保留：LLM 消息与结构化输出、工具与 MCP 边界、独立上下文、流程终止、失败传播、Token 与成本、结果质量对比。以当前实际编排为准，能解释模型决策与程序控制的分工；不把掌握框架内部实现作为首次部署的前置条件。

## 实践与记录方式

每次实践遵循：明确用户场景 → 设计交互与数据契约 → 阅读相关代码 → 完成一个端到端小功能 → 浏览器及接口验证 → 写入学习日志。

- 修改前明确问题、预期行为和验证办法，控制在一个可解释的小目标内。
- 记录原有行为、原因、修改依据、验证命令及实际结果；失败尝试同样有学习价值。
- 达到阶段验收标准后，在本计划更新进度并链接对应日志，不以“读过代码”代替掌握。
- 功能或修复与对应日志按 `AGENTS.md` 的规则组织；提交和推送分别等待用户明确指令。

| 文档 | 职责 |
| --- | --- |
| `docs/learning-plan.md` | 学习目标、范围、顺序、验收标准与进度 |
| `docs/learning-log.md` | 每次实践的问题、原因、方案与验证结果 |
| `docs/engineering-metrics-design.md` | 单任务工程指标的已确认范围、统计口径与实施验收依据 |
| `CONTEXT.md` | 稳定业务术语与已确认规则 |
| `README.md` | 项目介绍、运行说明与学习文档入口 |
| `AGENTS.md` | AI 协作、代码修改与 Git 操作规则 |
