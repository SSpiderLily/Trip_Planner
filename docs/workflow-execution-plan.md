# AI Agent 辅助开发工作流执行计划

状态：历史草案，文档拆分方案已被后续讨论替代，不作为当前执行依据。更新日期：2026-09-30。

后续讨论已明确精简文档，并将项目工作流与个人学习需求分开。本轮试运行及当前结论统一记录于 [CHG-001 工作流文档精简试运行](changes/CHG-001-workflow-trial.md)。下文保留初始方案供追溯，其中三个独立模板、四份独立角色协议及强制学习记录的设计不再作为当前目标。

本计划依据用户提供的《AI Agent 辅助开发工作流方案》，将其转化为可逐步执行和验收的落地任务。面向个人项目，先以当前旅行助手仓库试运行，再提炼可复用部分。本文落盘只表示计划已形成，不表示模板、Agent Contract 或真实需求试运行已经完成。

## 1. 方案判断

建议采用原方案的主干：规格驱动开发，以验收测试连接需求与实现，对复杂关键逻辑选择性使用 TDD。人负责需求、取舍、授权和最终验收；Agent 在已批准边界内完成设计、编码、验证和修复。

最有价值的设计是区分 Verification 与 Acceptance：测试通过只能证明已检查的行为符合规格，最终是否满足人的意图仍需人工验收。按风险设置设计审批，也适合个人项目控制沟通成本。

落地的主要风险是文档重复、审批反复、测试只验证实现自身，以及为了四种角色提前搭建复杂调度系统。因此 v1 保留原方案的四项交付物，先补齐执行语义，不增加平台、仪表盘、自动审批或多 Agent 编排。

## 2. 保留与补充的规则

以下补充均为建议，待确认后才进入正式工作流。

### 审批绑定版本

需求批准记录应包含批准人、时间、需求版本及对应确认内容。设计审批采用相同方式。用户在对话中明确批准即可，由 Agent 如实记录；Agent 不得代替用户批准，沉默不算批准。

需求范围或 AC 语义变化时递增需求版本，重新批准受影响部分；设计风险、外部接口或核心方案变化时重新评估设计审批。错别字和不改变语义的澄清无需重新审批。已经批准且未变化的内容不得重复索取授权。

需求批准、设计批准和最终验收不隐含 Git 提交、推送或部署授权。当前仓库继续遵守 AGENTS.md 的独立提交和推送授权规则。

### 阶段与阻塞分开

统一阶段名称，避免原方案中的 VERIFICATION 与 VERIFYING 混用：

```text
IDEA → REQUIREMENT → DESIGN → IMPLEMENTATION → VERIFICATION → ACCEPTANCE → DONE
```

在 REQUIREMENTS.md 顶部维护 Change 的唯一进度记录：Change ID、当前阶段、推进状态、需求版本、设计版本、下一步。推进状态使用 ACTIVE、WAITING_HUMAN、BLOCKED；等待正常审批与异常阻塞分开表达。

阻塞记录保留当前阶段，并写明原因、影响的 REQ/AC、建议返回阶段及需要的决定。只停止受阻和依赖它的工作；能够独立完成的授权工作可以继续。跨会话恢复先读进度、审批记录、相关差异和验证证据，不靠聊天记忆推断已批准。

### 风险按影响判定

LOW、MEDIUM、HIGH 的原有例子作为参考，最终结合影响范围、兼容性、数据与权限影响、可逆性判断。普通 CRUD 若涉及敏感数据、删除或权限，同样可能是 HIGH。

DESIGN.md 必须记录风险等级及理由；多个风险取最高等级。不确定且影响实质性方案时请人决策。LOW 自动推进，MEDIUM/HIGH 等待明确确认；风险在实现中升高时重新进入设计判断。

### 验收必须有证据

每条 AC 明确输入或前置条件、可观察结果、验证方法。验收方法可以是自动测试、接口检查或人工场景，不强制全部采用 E2E。

在 VERIFICATION.md 维护唯一的追踪表：

| AC | 关联需求 | 设计与任务 | 代码位置 | 验证方法及证据 | 结果 |
| --- | --- | --- | --- | --- | --- |
| AC-001 | REQ-001 | DESIGN 中的章节、TASK-001 | 文件或符号 | 测试节点或手动步骤、实际结果 | NOT_RUN |

结果使用 PASS、FAIL、BLOCKED、NOT_RUN；不适用的工具检查单独标记 N/A 并说明原因，不能用 N/A 跳过一条必需 AC。没有运行的测试不得写成通过。

证据注明验证时间、代码基线及未提交差异、命令或步骤、退出结果及必要摘要。验证后修改相关代码，重新运行受影响检查。采用 Change 内局部 ID，完整引用为 CHG-001/AC-001；自动测试优先引用实际测试名称，不额外维护一套重复 TEST 编号。

### 文档保持单一职责

REQUIREMENTS 记录意图与批准范围，DESIGN 记录方案与任务，VERIFICATION 记录证据与最终验收。Project Docs 记录已实现的系统现状；候选方案只放在 Change Docs。Project Docs 在提交最终验收前同步，不等 DONE 后再补。

小改动仍可保留三个简短文档，不要求填充无意义章节。架构、数据模型和决策文档按实际需要新增，不预先创建一组空文件。历史规格改变时保留版本和变更原因，避免覆盖后丢失原批准依据。

## 4. 分步执行

### 步骤一 确认工作流边界

人与 Agent 一起确认本计划的补充规则，尤其是版本审批、风险判定、状态位置和验证方式。将确认结论写入 DEVELOPMENT_WORKFLOW.md，明确 DoR、DoD、阶段入口与退出条件。

完成标准：针对 LOW 改动、MEDIUM 设计、AC 变更和验证失败四种场景，都能明确下一步及是否需要人参与。文档草拟和规则讨论无需启动产品代码修改。

### 步骤二 制作三个模板

| 模板 | 必需内容 | 完成标准 |
| --- | --- | --- |
| REQUIREMENTS | 进度、背景、目标、范围与非目标、约束、REQ、AC、待决问题、版本与批准记录 | 人能据此确认要做什么，AC 可观察且可验证 |
| DESIGN | 现状证据、方案与取舍、模块和契约变化、异常处理、风险、TASK、验证策略、设计批准记录 | Agent 无需猜测关键行为即可开始实现 |
| VERIFICATION | 代码基线、AC 追踪表、检查结果、审查发现、设计偏差、文档同步、限制、人工验收记录 | 人能复核完成证据，失败和未验证项清晰可见 |

使用一个简短虚构案例检查模板衔接；明确标注示例，不把示例审批或测试结果当作真实记录。

### 步骤三 编写四个 Agent Contract

每份 Contract 固定包含 INPUT、RESPONSIBILITY、MUST NOT、OUTPUT、EXIT CONDITION、NEXT STATUS 六项。

| 角色 | 核心责任 | 退出与交接 |
| --- | --- | --- |
| Requirement | 澄清意图，形成需求与 AC | 草案完整后等待人批准；批准后进入 DESIGN |
| Design | 阅读项目现状，确定方案、风险、任务和验证策略 | LOW 且满足 DoR 自动进入 IMPLEMENTATION；其余等待批准 |
| Coding | 按批准边界实现，执行针对性检查，记录偏差 | 任务完成且具备可审查证据后进入 VERIFICATION |
| Review | 核对需求、方案、代码与证据，检查遗漏与回归 | 实现错误退回 IMPLEMENTATION，设计或需求错误返回对应阶段；通过后进入 ACCEPTANCE |

v1 由同一 Agent 分阶段履行职责，使用 Contract 切换上下文。Review 必须独立核对 AC 和实际差异，不能仅转述 Coding 的完成说明。这不等同于独立审查者；若试运行暴露自审盲点，再考虑额外审查 Agent。

完成标准：四份 Contract 对阶段名称、权限、输入文件和交接条件保持一致；没有角色能自行批准需求或最终验收。

### 步骤四 跑通一个真实需求

选择范围小、有明确可观察行为、能够主要通过本地验证的真实需求。可考虑旅行日期校验或一个已有异常处理问题；这些只是候选，需检查现有实现并由人确认，不能预设项目存在缺陷。

执行顺序：

1. 检查工作区、分支和远程，保留已有修改，按仓库约定阅读相关文档与配置。
2. 建立 Change 目录，编写需求与 AC，取得 Gate 1 的明确批准。
3. 完成技术设计、风险判断和任务拆分；MEDIUM/HIGH 取得 Gate 2 批准。
4. 满足 DoR 后编码，按验证策略选择是否采用 TDD，记录实现偏差。
5. 执行必要验证及一致性审查，补齐证据和受影响的 Project Docs。
6. 提交可复核的结果与限制，请人进行 Gate 3 验收；确认后才标为 DONE。

完成标准：真实 Change 的三份文档齐全，必需 AC 均有验证证据，无阻塞审查问题，人工验收有明确记录。未获验收停留 ACCEPTANCE，不得标 DONE。Git 提交和推送按独立授权执行。

### 步骤五 复盘并决定是否迭代

在该 Change 的 VERIFICATION.md 中记录：人工介入次数及原因、重复审批、文档重复维护、遗漏的 AC、阶段回退及原因、验证受环境影响的情况。

以这些实际问题决定 v1.1 的调整，不预设要增加 Agent、CI 或更多表单。完成标准是能指出哪些规则帮助了交付、哪些造成额外负担，并给出保留或简化的具体决定。

## 5. 当前项目的验证适配

依据当前提供的项目约定，前端已有 `npm run build`，包含 vue-tsc 与 Vite 构建；没有现成的统一 lint 或单测脚本。正式设计时再次检查实际仓库，不能把尚不存在的检查当成门禁或标记通过。

新增测试设施应由试点需求和设计决定。后端可先选择适当的标准库测试或现有可用工具；需要引入依赖时纳入风险评估。纯文档修改检查链接、状态、规则一致性与差异即可，无需运行与之无关的应用构建。

涉及 LLM 和高德工具的需求，将稳定的契约检查与真实服务联调分开。替代响应可以证明结构、参数和异常处理行为；真实联调用于确认集成和行程效果。Mock 通过不能证明真实集成通过。若真实联调属于必需 AC 而无法执行，应记录 BLOCKED 并停留待验证状态。

对于行程合理性等非确定性目标，在需求阶段约定固定样例、评价维度和通过条件，保留必要且脱敏的结果摘要。密钥、真实用户数据和完整敏感模型响应不得进入证据文档。
