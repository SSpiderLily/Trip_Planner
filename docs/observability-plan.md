### 最小实现原则

增加表、模块、依赖或功能前，先问：没有它，当前核心闭环是否仍能跑通？如果能，则暂不增加；遇到具体阻塞再提出必要改动，新增范围先与用户确认。当前核心闭环是合法请求提交 → 独立任务执行 → 步骤增量记录 → 查询状态与最终结果；先验证成功和执行失败路径。

暂不增加 requests 表。参数拒绝仍按既定规则在输入端处理；在观测页面展示拒绝记录的已确认需求后置，不作为当前核心闭环的前置条件，也不因这个需求预先拆出新表。后置不等于已完成，具体存储方案到实施该需求时再决定。

## 记录与页面约定

一次请求对应一条 Trace，Agent、每轮模型、每次工具和解析校验各自形成 Span，错误捕获等作为事件。仅记录实际发生的操作，不预设调用轮数。业务分类不等于 OTel SpanKind。

最小记录包含：格式版本、trace/span/parent 标识、操作名称和类别、起止时间与耗时、操作状态、脱敏输入输出、截断标记、错误与相关事件。按需要补充 Agent、工具、模型、用量来源和代码/提示词版本；未知 Token 不填零。耗时不重复累加父子步骤。

分开表示 HTTP 状态、业务结果、执行中断和记录完整性；记录不完整不自动等于业务失败。UI 请求列表、调用树和详情共用这一约定。运行中步骤必须在开始时可见，不能仅等 Span 结束再导出。

示意结构（虚构，非运行证据）：

```text
一次规划
├─ 获取/初始化规划器
└─ 规划执行
   ├─ 景点 Agent
   │  ├─ 模型调用
   │  ├─ 景点搜索工具
   │  └─ 模型使用工具结果
   ├─ 天气 Agent：失败 → 终止规划
   └─ 酒店、最终规划：未执行，不生成虚构调用记录
```

## 任务接口契约（设计，尚未实现）

任务管理负责身份、状态、执行安排和最终结果；线程池只提供同步代码的执行位置，观测记录负责解释过程。每次合法提交返回唯一 task_id，失败任务同样有 ID。先完成登记和执行安排，再返回已接收；登记失败拒绝请求且不启动模型。

| 拟议接口 | 返回约定 |
| --- | --- |
| `POST /api/trip/tasks` | 输入合法且当前空闲时返回 HTTP 202、task_id 和 accepted 状态，表示已接收而非已完成；输入校验失败或已有活动任务时不启动新任务、不排队；忙时返回 HTTP 409、TASK_BUSY，前端提示已有规划正在执行 |
| `GET /api/trip/tasks/{task_id}` | 查询成功返回 HTTP 200，包含任务状态、当前步骤和步骤开始时间；任务失败仍返回 200 并携带脱敏错误摘要；不存在返回 404，查询自身内部错误返回 500 |
| `GET /api/trip/tasks/{task_id}/result` | 与高频状态查询分开获取完整行程；成功返回 HTTP 200 与行程；运行中返回 HTTP 409、RESULT_NOT_READY；失败/中断分别返回 HTTP 409、TASK_FAILED / TASK_INTERRUPTED 与错误摘要；任务不存在返回 404 |

状态查询只读取必要字段，不加载完整行程和消息再裁剪。任务失败后 current_step 为空，返回 finished_at 以及 error 中的失败步骤、稳定错误码和脱敏说明；步骤详情仍保留起止时间。失败或中断是终态，不能表述为“尚未准备好”。

首页迁移为提交任务 → 查询状态 → 获取结果，切换完成后移除旧 `/api/trip/plan` 接口。浏览器保存当前 task_id，刷新后继续查询；历史已清理时显示记录不存在并清除失效 ID。参数被拒绝的请求尚未开始任务，其观测关联标识需与 task_id 明确区分。任务与 Trace 的映射也需覆盖多次状态/结果查询，不为每次查询重新创建规划任务。

## 数据模型草案与写入边界

数据库采用本地 SQLite，以下为字段与约束草案，不是已完成迁移的数据库结构。

### SQLite 使用边界

- 一个本地数据库保存 tasks、task_results、spans，满足单进程、单活动任务及历史查询的学习场景，不部署独立数据库服务。
- 保持短事务，模型和工具调用在事务外执行；业务结果与成功状态原子提交，观测详情写入独立处理。
- 拟采用 WAL 改善查询与写入并存的场景，但它仍然只有一个写入者；连接归属、锁等待上限和退出刷新策略在实现时验证，不无限重试或无保护地共享连接。
- 数据库放入独立本地数据目录，配置经 config.py 读取；数据库及 WAL/SHM 等运行文件均排除 Git。容量治理不能只计算主数据库文件。
- 时间统一为固定精度 UTC ISO 8601 文本，JSON 统一序列化为 TEXT；输入校验与 JSON 结构检查在应用层完成。建表草案见下，不另建数据库设计文档。

并发和 WAL 边界参考 [SQLite 官方说明](https://www.sqlite.org/wal.html)；选型已确认，具体初始化配置尚未实现。

| 表 | 职责与字段草案 |
| --- | --- |
| `tasks` | task_id 主键、状态、执行所需 request_data、接收/开始/结束时间、脱敏错误码与说明 |
| `task_results` | task_id 唯一关联任务、最终行程；一个任务零或一个最终结果 |
| `spans` | span_id 主键、task_id、parent_span_id、名称/类型、状态、起止时间、脱敏限长输入输出与错误；一个任务多个步骤 |

parent_span_id 关联具体父步骤的 span_id，不能用 agent_id 替代；同一个 Agent 可执行多次。顶层步骤的父标识为空。需约束父子步骤属于同一任务，避免跨任务关联。Agent 名称或标识作为筛选元数据。

步骤开始时插入 running 记录与开始时间，结束时间为空；完成后更新结束状态、结果或错误。先保存开始记录才能展示进行中步骤并定位中断位置；记录最后停留位置不等于证明崩溃根因。

任务接收与实际开始时间分开，区分登记/调度间隔与执行耗时；accepted 仅是短暂启动状态，不表示有等待队列。状态查询与结果查询分开读取；最终行程、成功状态和结束时间在同一短事务提交。模型/工具调用在事务外进行；详细观测写入与业务结果提交隔离，避免观测失败阻断业务。最终结果保存失败时明确提示结果保存失败，不报告已成功保存，不增加备用存储。

本草案尚未覆盖输入校验被拒绝的请求，它不应成为失败任务；其观测展示与存储方案后置，当前不增加 requests 表。清理以已结束任务为单位，在同一短事务中删除任务、对应行程结果及全部 Span，不保留孤立详情，不清理活动任务。容量阈值与截断约定见下，具体清理和空间回收方式在实现时验证。按任务查询步骤的索引作为已有查询的实现细节处理。

### tasks 最小字段定义（设计）

运行边界：第一版单后端进程只允许一个活动任务，每个任务内部 Agent 顺序执行；历史任务仍可查询。以下解释字段语义，SQLite 约束见建表草案。

| 字段 | 逻辑类型 | 可为空 | 用途与约束 |
| --- | --- | --- | --- |
| task_id | 字符串 | 否 | 主键，唯一标识一次合法输入发起的规划 |
| status | 枚举字符串 | 否 | accepted / running / succeeded / failed / interrupted |
| request_data | JSON 对象 | 否 | 通过校验的旅行需求；不混入服务密钥、认证信息或完整模型响应 |
| created_at | UTC 时间 | 否 | 接收登记时间 |
| started_at | UTC 时间 | 是 | 实际开始时间；尚未执行时为空 |
| finished_at | UTC 时间 | 是 | 已知的成功或失败结束时间；无法确定实际结束时间的中断任务留空 |
| interruption_detected_at | UTC 时间 | 是 | 重启检查发现遗留任务中断的时间，不冒充实际退出时间 |
| error_code | 字符串 | 是 | 失败或中断的稳定分类，正常任务为空 |
| error_message | 字符串 | 是 | 脱敏且限长的错误摘要，正常任务为空 |

状态转换：accepted → running → succeeded/failed；启动执行安排失败可由 accepted → failed；重启接收新任务前将上次进程遗留的 accepted/running 标为 interrupted，不重跑。终态不退回 running；再次提交创建新 task_id。输入被拒绝不进入 tasks。

任务 succeeded 必须与 task_results 的结果同事务提交；failed 保存结束时间和错误摘要；interrupted 保存发现时间与中断原因，不能用重启时间计算精确执行耗时。已成功/失败步骤保持原样，仅遗留的运行中步骤标为中断。

当前步骤由 spans 的执行关系确定，不在 tasks 重复保存步骤名称和时间；查询返回最内层活动步骤，避免把同时打开的父 Span 误当成多个并行操作。观测缺失时不可据此推断任务停滞。记录完整性标记与存储故障下的查询方式仍需细化，本字段表不代表所有故障设计已完成。

### task_results 最小字段定义（设计）

task_id 同时作为主键和关联 tasks.task_id 的外键；result_data 非空，保存经过结构和业务校验的完整行程 JSON。一个任务最多一份结果，不增加独立结果 ID；第一版不拆景点、酒店和餐饮表。失败或中断任务没有结果行，错误摘要保存在 tasks。结果插入和任务成功状态更新在同一短事务提交。

### spans 最小字段定义（设计）

| 字段 | 用途与约束 |
| --- | --- |
| span_id | 主键，标识一次具体执行，不是 Agent 的固定 ID |
| task_id | 关联所属任务，按任务查询步骤时建立索引 |
| parent_span_id | 关联父步骤；顶层为空，父子必须属于同一任务 |
| name | 埋点提供的固定操作名，如 agent.attraction、llm.invoke、tool.amap_maps_weather；不拼接城市或用户输入，不增加动态标题 |
| operation_type | planning / agent / llm / tool / validation 等业务类别 |
| status | running / succeeded / failed / interrupted；仅为实际开始的操作创建记录 |
| started_at | 开始时间，创建记录时填写 |
| finished_at | 已知结束时间，运行中或无法确定结束时间的中断记录为空 |
| input_data | 脱敏、限长的执行输入，按类别保存 JSON 兼容内容；不是 tasks.request_data 的机械副本 |
| output_data | 脱敏、限长的实际输出；未返回时为空，不能伪造成功输出 |
| error | 可空对象，包含错误码和脱敏说明；任务可保存业务失败摘要，不依赖该详情写入成功 |
| input_truncated / output_truncated | 是否因大小上限截断，明确区别完整与部分内容 |

运行中步骤先插入，再在调用结束后更新；不能用“字段为空”自行推断失败。输入为空、正常空输出、未返回和记录缺失的区别由操作状态、输出语义及记录完整性共同表达。工具正常空结果时工具 Span 可成功，所属业务步骤因信息不足失败；祖先失败不回写已成功的子步骤。状态查询和调用树读取摘要字段，点击步骤再取输入输出详情，不新增详情表。

观测层仅接收执行边界报告的事实，负责标识、关联、计时、脱敏和保存，不查询额外业务信息、不解释旅行需求、不参与业务成功判定。变化的参数放 input_data，固定操作名可在页面映射为中文；字段和交互只增加到满足既定观测需求为止，不引入动态标题、模型生成说明或提前设计的扩展元数据。

### 建表 SQL 草案（尚未接入应用）

约束负责主键、关联、必填与枚举取值；任务管理层通过带原状态条件的更新控制状态转换并检查更新行数，不增加业务触发器。每个连接在事务外启用外键；父子任务一致性使用复合外键，其目标需有对应唯一约束，参考 [SQLite 外键说明](https://www.sqlite.org/foreignkeys.html)。文本主键显式声明 NOT NULL，参考 [建表说明](https://www.sqlite.org/lang_createtable.html)。

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE tasks (
    task_id TEXT PRIMARY KEY NOT NULL,
    status TEXT NOT NULL CHECK (status IN
        ('accepted', 'running', 'succeeded', 'failed', 'interrupted')),
    request_data TEXT NOT NULL,
    created_at TEXT NOT NULL,
    started_at TEXT,
    finished_at TEXT,
    interruption_detected_at TEXT,
    error_code TEXT,
    error_message TEXT
);

CREATE TABLE task_results (
    task_id TEXT PRIMARY KEY NOT NULL
        REFERENCES tasks(task_id) ON DELETE CASCADE,
    result_data TEXT NOT NULL
);

CREATE TABLE spans (
    span_id TEXT PRIMARY KEY NOT NULL,
    task_id TEXT NOT NULL REFERENCES tasks(task_id) ON DELETE CASCADE,
    parent_span_id TEXT,
    name TEXT NOT NULL,
    operation_type TEXT NOT NULL CHECK (operation_type IN
        ('planning', 'agent', 'llm', 'tool', 'validation')),
    status TEXT NOT NULL CHECK (status IN
        ('running', 'succeeded', 'failed', 'interrupted')),
    started_at TEXT NOT NULL,
    finished_at TEXT,
    input_data TEXT,
    output_data TEXT,
    error TEXT,
    input_truncated INTEGER NOT NULL DEFAULT 0 CHECK (input_truncated IN (0, 1)),
    output_truncated INTEGER NOT NULL DEFAULT 0 CHECK (output_truncated IN (0, 1)),
    UNIQUE (task_id, span_id),
    CHECK (parent_span_id IS NULL OR parent_span_id <> span_id),
    FOREIGN KEY (task_id, parent_span_id) REFERENCES spans(task_id, span_id)
        DEFERRABLE INITIALLY DEFERRED
);
CREATE INDEX spans_by_parent ON spans(task_id, parent_span_id);
CREATE INDEX tasks_by_created_at ON tasks(created_at);
```

复合唯一索引同时支持按 task_id 查询，不重复建相同前缀索引。父 Span 先登记，子 Span 再登记；父关联创建后不可改，采集器保证不形成环。父记录丢失时不伪造父记录或把子步骤改成根步骤，标记记录不完整并跳过无法关联的持久化，业务继续。清理只删除已结束的任务，由任务外键级联删除结果和步骤，延迟父步骤外键在事务提交时检查。状态与时间的配套关系、JSON 合法性和“成功必有结果”由应用校验及事务保证，本 SQL 不独立保证这些业务规则。

### 容量与保存失败约定

默认保留 7 天，总容量治理目标 200 MiB，计入数据库与 WAL/SHM；每个 Span 的 input_data、output_data 各限 64 KiB，均可配置。先脱敏再按 UTF-8 序列化字节数限长；截断内容封装为有效 JSON 预览并标记，不能直接切断 JSON 后存为损坏内容，大小包含封装开销。

优先按结束时间（中断使用发现时间）清理最旧已结束任务，不删除活动任务。清理历史后仍不足则停止保存观测详情，保留必要状态写入的尝试并提示不完整；200 MiB 是治理目标，不承诺硬性磁盘上限。删除记录未必立即缩小物理文件，WAL 检查点和空闲页回收在实现时验证。

| 保存位置 | 失败处理 |
| --- | --- |
| 接收登记 | 拒绝新任务，不启动模型，释放名额 |
| Span 详情 | 业务继续；提示记录不完整，不覆盖原业务错误 |
| 最终结果事务 | 回滚成功状态与结果，报告结果保存失败；数据库可写时登记 failed 和 RESULT_SAVE_FAILED；不可写时不得伪报终态已持久化，不增加备用结果存储 |

### 任务执行流程

1. 启动时先完成遗留 accepted/running 任务及运行中 Span 的中断处理，再开放任务接收；恢复处理失败时不接收新规划。
2. 校验输入，在后端原子检查并占用唯一执行名额；忙时返回 TASK_BUSY，不登记待执行任务。
3. 短事务插入 accepted，安排由应用生命周期持有的执行任务，再返回 202 和 task_id；安排失败则尝试登记 failed 并释放名额。
4. 执行开始更新 running；同步初始化和规划在线程池中执行，任务内 Agent 顺序调用，每次规划独立历史。模型与工具调用不占数据库事务。
5. 操作开始/结束分别保存 Span。任务执行不依赖 HTTP 连接；第一版可直接以 task_id 关联一次规划的 Trace，轮询不另建规划 Trace。
6. 成功时同事务保存结果、更新 succeeded 与结束时间；业务失败保存 failed、结束时间和错误摘要，详细 Span 单独处理。最后释放执行名额，断连不释放名额。
7. 前端保存 task_id，每 2 秒轮询状态及步骤摘要，避免重叠请求；终态停止自动轮询，成功再取结果，步骤详情按点击读取。查询故障显示查询失败，不推断规划已失败；不可恢复的终态保存故障提示方式仍需验证。

### 后端职责与文件映射（设计，文件尚未新增）

沿用现有目录，第一版新增三个有明确职责的服务文件；先实现具体类，不增加通用仓储基类、事件总线或插件系统。

| 文件（相对 backend/app） | 负责的事情 | 边界 |
| --- | --- | --- |
| `api/routes/trip.py`（修改） | 接收输入、调用任务服务、将返回值/错误映射为 HTTP；承载任务状态、结果及观测查询入口 | 路由不持有后台执行生命周期，不直接写 SQL 或编排四 Agent |
| `services/task_service.py`（新增） | 唯一执行名额、登记与执行安排、后台执行引用、状态转换、结果交付、重启中断处理；协调查询和当前进程故障提示 | 单进程单实例，由应用持有；同步初始化与规划进入线程池；不解释工具返回值，不拼 SQL |
| `services/task_repository.py`（新增） | SQLite 初始化、连接与短事务；三表读写、摘要/详情查询、整任务清理 | 一个具体存储模块即可；不执行 Agent，不吞掉写入错误，由调用者按业务或观测路径分别处理 |
| `services/observation_service.py`（新增） | Span 开始/结束、父子上下文、固定名称、计时、脱敏、截断；捕获观测保存错误并报告记录缺失 | 不决定规划成功，不查询额外旅行信息；调用 repository 保存，不将任务结果当作观测详情 |
| `agents/trip_planner_agent.py`（修改） | 四 Agent 顺序编排、每次规划历史隔离、真实工具成功证据、必要步骤失败传播、行程校验；在实际执行边界接入采集 | 业务证据由执行侧维护，观测关闭仍能判定成功/失败；不依赖数据库查询作业务决策 |
| `models/schemas.py`（修改） | 输入日期一致性校验、任务状态/错误/结果及观测查询响应结构 | HTTP 数据契约不等于数据库行；不复制完整消息到高频状态响应 |
| `api/main.py`（修改） | 创建并持有 repository、观测服务与任务服务；启动恢复完成后接收规划；关闭时管理后台执行及资源 | HTTP 请求只借用服务实例；正常退出先停止接收并协调执行，强制退出靠下次启动识别中断，不把取消等待当成同步调用已停止 |
| `config.py`（修改） | 数据库路径、保留天数、容量和内容上限等配置 | 沿用现有配置入口，运行文件排除 Git |

依赖方向：路由 → 任务服务 → 规划器；任务服务 → repository；规划器的埋点 → 观测服务 → repository。应用入口负责组装。任务服务保存业务状态和结果，观测服务保存过程；共用 SQLite 不代表共用错误处理策略。

任务身份由任务服务创建并传入执行上下文，采集器生成 span_id 并管理父子关系。异常示例：天气工具报错 → 执行侧识别并抛出业务错误 → 观测侧尝试记录失败 Span → 任务服务保存 failed；观测写入异常不得替换天气错误。

LLM 与工具细节采集仍需验证安装版本的实际扩展入口。仅包住四次 Agent.run() 能记录 Agent 层，无法得到每轮消息与实际工具结果；`llm_service.py` 当前仅创建共享 LLM，`amap_service.py` 也不覆盖规划器自行创建的 MCP 工具。实施模型/工具采集阶段再按已验证接口决定最小适配方式，不直接修改 venv 或全局打补丁。

落地顺序：先完成业务失败传播和历史隔离；再用替代规划器验证 repository + task_service + 新任务路由的成功/失败/忙时拒绝闭环；随后接真实规划器和 Agent 层采集，最后补模型/工具内部采集与观测页面。测试沿用 backend/tests 的 unittest，分别验证存储约束、任务生命周期、采集故障隔离与 HTTP 契约。

## 实施时需验证的细节

- 天气未知在响应与页面中的具体表示需设计；已确认日期覆盖不足可继续，模型未调用对应工具或必要查询为空仍是步骤失败。
- 独立执行生命周期与前端轮询按下述流程实现；验证启动失败、断连、刷新和重启路径。
- 容量与故障策略已确认；记录完整性标记、数据库完全不可写时的当前进程提示渠道及重启后的可知范围仍需落实，不能承诺故障提示也一定持久化。

## 执行与记录

先核实未知代码行为，再逐项确认业务语义。隔离状态和取消备用行程作为独立业务改动验证，不以“无侵入观测”掩盖行为变化。测试以替代依赖为主，真实 API 用于集成验收。

已发生的问题与验证证据见[学习日志](learning-log.md)；学习路线只链接本计划，不复制阶段进度。提交和推送仍需对应明确指令。

成功证据由执行层在当前规划内判定，不能依赖观测存储是否可用；测试需覆盖未调用工具、只出现调用文本、工具返回业务错误、正常空结果，以及工具成功但观测写入失败的情况。正常空结果不得误计为工具调用错误；其所属业务步骤和整次规划标记失败。

天气验收覆盖：日期全部匹配、部分匹配、完全不匹配但返回有效预报、真正空结果和调用错误。前三类按覆盖程度展示真实预报/天气未知，后两类失败；不得让模型将不匹配日期的数据重标为旅行日期。

行程契约验收覆盖：结构合法但少一天、多一天、重复日期、日期缺口、起止日期偏移和正常匹配。记录具体失败字段/规则；不通过时返回明确错误，不自动补造内容。该校验不代表路线合理性或景点真实性已被全面验证。

输入契约测试必须验证冲突请求被拒绝，且规划器初始化、模型调用和工具调用次数均为零；不能只检查 HTTP 错误码。

观测采集需覆盖路由参数校验之前的请求入口，使参数拒绝可关联和查询；错误详情同样脱敏限长。验收同时检查拒绝记录存在、无 Agent/工具执行记录、规划执行失败率未受影响。
