# 智能体观测实施计划

更新时间：2026-09-26。

## 目标、范围与基线

目标是在本地学习并排查“请求 → Agent → 每轮 LLM/工具 → 结果校验/降级”的完整过程，同时为后续新增 Agent、工具和流程提供可复用的观测入口。

已完成应用源码静态核对和计划整理；本地一键启动经自动检查，用户确认已生成行程结果。由于尚未核实该请求的模型/工具调用和备用方案状态，阶段 0—5 均未完整验收。实际代码结构、已发现的限制和虚构展示示例见[实现现状与目标结构](observability.md)。观测实践对应[学习计划](learning-plan.md)中的请求链路、LLM、工具调用和可靠性阶段。

拟采用应用内薄封装 + OpenTelemetry SDK + 本地结构化导出，再接本地 Langfuse。具体 SDK 版本、回调入口和导出兼容性在实施时验证，不预设当前 HelloAgents 已自动适配。第一版不包含自建复杂前端、自动重放、提示词平台或生产自动部署。

## 阶段 0：本地运行与调用链核实

**目标**：获得真实运行基线，确认框架内部观测入口。

**实施步骤**：

1. 检查可用 Python/虚拟环境、Node/npm、`uvx` 和依赖版本；环境变量只报告是否配置。`requirements.txt` 的 HelloAgents 约束是范围，不能当作实际安装版本。
2. 使用根目录 `dev.py` 同时启动两端；首页和基础 `/health` 已验证，用户确认行程结果已生成。继续核对 API 地址、CORS 和该结果的真实来源。
3. `/api/trip/health` 的旧单 Agent 属性引用已修复，并以替代规划器验证 200/503；本阶段仍需在真实本地环境验证初始化及外部依赖状态，不能把隔离测试当作阶段验收。
4. 阅读实际安装版本的 SimpleAgent、LLM 与展开工具实现，确认调用方法、消息构造、循环结束条件、是否流式、Token 来源、工具错误表达。
5. 检查共享 Agent 的历史与线程安全，记录初始化在线程池外、规划在线程池内的边界。必要修复单独处理。

**交付**：实际运行命令与版本、调用链、埋点位置、阻塞问题清单。

**验收**：完成一次真实请求，区分模型结果和备用结果。若依赖不可用，记录为阻塞而非验收通过；替代依赖测试不能代替真实联调。

## 阶段 1：统一追踪基础

**目标**：每次请求可关联，各请求上下文相互隔离。

**实施步骤**：

1. 新增 `backend/app/observability/`，集中处理 SDK 初始化、薄封装、脱敏和导出；配置接入 `backend/app/config.py`。
2. 请求入口创建 Trace，正常与错误响应返回 `X-Trace-ID`；需要浏览器读取时配置 CORS `expose_headers`。避免自动埋点与手动埋点重复创建请求 Span。
3. 验证上下文穿过 `run_in_threadpool`，不把当前请求 ID 存在全局规划器、LLM 或工具实例上。
4. 日志关联 Trace/Span。本地 JSONL 按行导出结构化记录，设置长度与容量限制、轮转和 Git 忽略规则；导出文件不是业务数据存储。
5. 支持禁用观测、有限队列与失败处理；导出异常不得替换原业务结果或异常。

**交付**：统一观测入口和一条完整请求记录。

**验收**：正常/异常请求都有结束记录；两个并发请求不串上下文；禁用或导出失败不改变业务行为；敏感字段被过滤。使用替代依赖测试，避免为基础能力反复消耗真实 API。

## 阶段 2：Agent 编排与降级

**目标**：定位哪个 Agent 耗时、哪个步骤失败、为何生成备用数据。

**实施步骤**：

1. 为规划器获取/初始化、`plan_trip()` 和四次 Agent 执行创建父子 Span；初始化仅在实际发生时记录。
2. 记录 Agent 名称、输入输出摘要和耗时，保持现有顺序执行。
3. 为 JSON 提取/解析、TripPlan 校验及 `_create_fallback_plan()` 增加观测。
4. 在两个异常捕获分支记录原始失败阶段；将失败操作关联到降级事件，整次规划设置 `business.outcome=degraded`。
5. 备用方案自身失败时记录为 failed；不能把所有异常一律当作降级成功。第一版业务结果字段用于观测，不默认改变现有 API 响应契约。

**交付**：Agent 级调用树、可辨认的正常/降级/失败记录。

**验收**：覆盖正常输出、Agent 异常、无合法 JSON、模型字段错误和备用方案失败；HTTP 200 的备用响应也能从观测中识别。

## 阶段 3：LLM 与工具调用

**目标**：完整展开 Agent 内部一次“模型 → 工具 → 模型”的过程。

**实施步骤**：

1. 按阶段 0 核实的入口接入 LLM 回调或适配器，记录实际请求模型名、轮次、消息顺序、响应摘要、耗时和可获得的用量。
2. 在规划器注册展开工具时增加包装，保留 Tool 接口、名称、描述、参数与返回行为，继续显式注册 `auto_expand=False`。
3. 区分执行异常、MCP/工具返回的明确业务错误和正常空结果；记录开始、结束和实际调用次数。
4. 如果框架使用流式结果，在消费结束、异常或提前关闭时结束 Span，不提前吞掉或耗尽迭代器。
5. 增加显式开启的本地详情模式：先脱敏再保存，限制长度并标记截断；异常消息、堆栈和工具返回也适用。Token 缺失显示未知。
6. 仅记录实际可证实的终止原因与重试，不从字符串片段推定工具执行，也不虚构固定轮数。

**交付**：LLM 与工具级调用记录及展开详情。

**验收**：一次完整工具循环可追踪；记录次数与实际调用次数一致；无工具调用时没有工具 Span；开启前后参数和结果一致；保留现有工具注册测试并补充调用包装验证。

## 阶段 4：接入查看界面

**目标**：通过现成界面查询、展开并解释执行记录。

**实施步骤**：

1. 本地部署 Langfuse，先用合成样例验证选定 SDK/导出协议与父子关系，再接业务记录。
2. 配置请求列表、调用树和详情展示，验证业务降级、错误、耗时和消息内容的映射。
3. 通过同一个 Trace ID 关联本地日志，支持筛选失败/降级请求。
4. 明确进行中请求的展示限制：Span 结束后导出不等于实时进度。先使用关联日志观察运行中事件，实时推送另行设计。

**交付**：本地查看界面、实际启动与排障说明。

**验收**：可在界面解释一个成功请求和一个降级请求，父子关系与调用次数正确；观测平台停机后业务仍可运行。

## 阶段 5：可靠性与扩展

**目标**：形成持续可用、方便扩展的观测基础。

**实施步骤**：

1. 复用现有 unittest 方式，建立正常、工具超时/错误、输出不合法、并发、导出不可用的固定案例；大部分使用替代模型和工具。
2. 检查上下文清理、错误下的 Span 结束、脱敏、队列上限、文件保留和退出时有限刷新。进程强制退出无法保证所有记录落盘，文档需说明。
3. 记录代码版本及是否存在未提交修改、提示词版本、模型配置摘要；不要保存密钥。
4. 汇总耗时、工具错误率、降级率和有来源的 Token 用量；定义统计分母，区分请求级与调用级，避免父子耗时重复相加。
5. 写明新增 Agent/工具的接入范例；比较开启观测前后的行为与额外开销。

**交付**：针对性测试、接入约定、日常排障说明和基线对比。

**验收**：新增 Agent/工具能沿用统一入口；上述异常案例通过；真实 API 完成集成验收；观测服务故障不会拖垮业务。
